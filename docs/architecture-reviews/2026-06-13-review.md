## Executive summary

The codebase is moving in the right product direction: deterministic control-plane core, operator-console-first surfaces, and ledger-backed workflow actions. The strongest architectural shape today is:
- `OperationalCase` as the durable operational issue record
- `WorkItem`/operator views as the projection layer
- connector and semantic registries as contract boundaries
- workflow action ledger as the source of truth for automation state

The main architectural concern is no longer branch destructiveness; it is **where the platform is still too permissive or too broad**:
1. the semantic registry still operates in advisory mode in important downstream paths,
2. RBAC is still internal/coarse rather than project-scoped,
3. operator-surface growth is at risk of becoming endpoint sprawl before a tighter shared activity/query model lands.

## 1) OperationalCase / WorkItem vs Atlassian patterns

### Current state
The base branch already carries meaningful Atlassian/Jira-like patterns in:
- `app/brain/work_items.py`
- `app/brain/operational_cases.py`
- `app/brain/operator_views.py`

The important positive signals are already present:
- project-key projection (`case_project_key`)
- issue-type projection (`case_issue_type`)
- status-category projection (`case_status_category`)
- JQL-like parsing/filtering (`parse_case_jql`)
- built-in views and faceting (`builtin_case_views`, `facet_case_queue`)
- deterministic workflow transitions on `OperationalCase`

### Best branch in this area
`n2-pro-work-management` is the clearest architectural improvement.

It adds the missing work-management semantics operators actually need without creating a second source of truth:
- `sla_target_seconds`
- `due_at`
- owner-visible policy
- latest evidence / timeline fields
- last-event and event-count query semantics

That is the right shape: **OperationalCase remains canonical, WorkItem remains projectional**.

### Remaining gap
This is still not a full Atlassian-grade work-management model because the platform does not yet expose:
- project-level workflow schemes
- tenant-configurable issue-type schemes
- rank/backlog/board configuration
- persisted saved filters / shared views as durable config objects
- project-scoped permissions

**Board view:** good trajectory, especially in `n2-pro-work-management`; mergeable in slices.

## 2) Semantic registry as canonical source of truth

### What is working
`app/brain/semantics/metric_registry.py` is strong as a registry contract:
- canonical keys + aliases
- allowed source lists
- family compatibility
- evidence requirements
- value-kind checks
- case/report/surface-specific validation helpers

`app/brain/connector_registry.py` uses that registry well for connector certification and emitted-metric validation.

### What is still weak
The platform still does not enforce the registry as the blocking source of truth on every downstream path.

The clearest evidence is in `app/brain/operational_cases.py`, where `_metric_registry_metadata()` calls:
- `validate_metrics(report.metrics, strict=False)`
- and records `metric_registry_mode: advisory`

That means unknown metric drift is observed and annotated, but not consistently rejected, during case generation.

This is the single biggest architectural gap in the reviewed scope.

### Board view
- No reviewed branch creates a shadow metric registry.
- `N2-Pro/connector-platform` stays clean.
- But the repo still needs a follow-up change that upgrades advisory validation to blocking validation at the right ingestion boundaries.

**Recommendation:** keep merge decisions branch-scoped, but track semantic enforcement as a repo-level blocker before larger operator-surface expansion.

## 3) Connector platform separation: adapter / service / storage

### Current state
The connector platform remains well-shaped:
- registry contract in `app/brain/connector_registry.py`
- runtime/config boundary in `app/brain/config.py`
- secret-reference boundary in `app/brain/secret_refs.py`
- persistence abstractions in `app/brain/storage.py`
- operator-facing readiness projection in `app/brain/operator_api/connectors.py`

The important thing is that connector branches are not tunneling around the platform core. The reviewed connector work remains projectional and contract-driven.

### Branch assessment
`N2-Pro/connector-platform` is small and aligned.
It only exposes more executor metadata in readiness surfaces and leaves the underlying separation intact.

**Board view:** merge-ready.

## 4) Workflow automation: idempotency, approval gates, audit

### Current state
The base workflow model is good because automation state is ledger-backed rather than report-text-backed:
- idempotency keys in `app/brain/workflow_action_ledger.py`
- approval state and execution state as explicit fields
- approval decision records
- audit event generation tied to ledger state

This is the right architecture for an operations control plane.

### Branch assessment
`N2-Pro/workflow-automation` improves the system in the right way:
- adds internal workflow action projections
- adds approval queue and execution queue views
- adds workflow action audit surfaces
- validates audit approval requests against ledger records
- expands simulation coverage

That means it improves **workflow observability without bypassing approval/audit controls**.

### Remaining gap
The platform still does not have a richer project/workflow-scheme layer comparable to Jira workflow configuration. Automation is still case-scoped and internal. That is acceptable for now, but it is the next architectural ceiling.

**Board view:** merge-ready candidate after rebase.

## 5) Trust / Admin / Security

### Current state
Trust controls are present but intentionally narrow:
- internal operator roles in `app/brain/operator_auth.py`
- business allowlisting
- safe actor labeling
- audit store + export
- redaction utilities

### Branch assessment
`N2-Pro/trust-admin-security` is a clean hardening branch:
- tightens global-scope denial semantics
- hardens audit export redaction
- collapses secret-shaped business labels in internal API data

This is strong defensive work and respects the current trust boundary design.

### Remaining gap
RBAC is still coarse:
- `viewer`
- `operator`
- `admin`

That is enough for internal operator tooling, but not yet for the long-term admin/control-plane model. There is still no project-level permission scheme or delegated tenant-admin contract.

**Board view:** merge-ready candidate after rebase.

## 6) Operator surfaces and strategic alignment

### What is good
`N2-Pro/operator-surfaces` is clearly aligned with the product direction:
- console-first, not WhatsApp-first
- owner brief surfaces
- suggested actions
- recent case activity projections
- expanded tests around operator-facing APIs

### Why it still needs work
This branch is simply too broad right now (`55 files`, `+5646/-277`) and it starts to fragment the API surface into many specialized endpoints (`recently_opened`, `recently_acknowledged`, `recently_assigned`, etc.).

That is where the architecture starts drifting away from the more Atlassian-like model already present in `operator_views.py`, which prefers:
- one query surface
- facet/sort/filter semantics
- reusable projections over route proliferation

### Board view
The direction is correct, but the branch should be split into smaller merges:
1. common activity/recent-case projection primitives
2. recent-case API surface
3. owner brief / suggested actions
4. runs dashboard delivery additions

**Verdict:** needs work before merge.

## Recommended next architectural moves

1. **Tighten semantic enforcement**
   - Promote unknown/cross-family metric validation from advisory to blocking at case/report ingestion boundaries.

2. **Land work-management before broad UI expansion**
   - Merge `n2-pro-work-management` before larger operator-surface branches.

3. **Keep workflow ledger canonical**
   - Continue adding projections and admin affordances on top of `workflow_action_ledger.py`; do not create a parallel automation state model.

4. **Introduce a shared activity model before more `recently_*` endpoints**
   - Prefer one reusable case-activity projection plus filters over endpoint-per-transition sprawl.

5. **Plan the next trust layer**
   - Evolve from coarse internal roles to project/tenant-scoped permissions once operator surfaces expand beyond internal-only use.
