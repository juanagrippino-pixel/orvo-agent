## Executive decision

The current control-plane branch remains architecturally aligned with Orvo's accepted direction: a deterministic D2C ecommerce operations control plane with Atlassian/Jira-like work-management surfaces, not a chatbot or report-first shortcut.

Since the earlier 2026-06-06 ARB report, the canonical branch materially improved in three areas:

1. **WorkItem priority drift was closed** by `e2280b8` / `4fccf16`: priority brackets now live in `app/brain/work_items.py` and are reused by operator API code.
2. **Mutating internal case actions now require an idempotency key at the HTTP boundary** by `5c98742`: `POST /internal/brain/businesses/<business_id>/cases/<case_id>/actions` calls `require_case_action_idempotency_key()` before mutation and uses the pre-ledger action path.
3. **JQL/internal error redaction tightened** by `0250e18` and `c69b03e`: JQL error echo tests exist, and internal error messages are passed through redaction before response.

The biggest remaining architecture risk is now **surface/query proliferation**, not core product misalignment. WorkItem is still correctly projection-only, but JQL/view/facet fields are split between WorkItem semantics and route/view code. The new `codex/eng-factory-workitem-query-field-registry-20260606` branch is the best next small integration candidate because it moves query-field vocabulary into WorkItem projection semantics without turning business measurements into ad hoc metrics.

## 1. OperationalCase / WorkItem against Atlassian patterns

### Aligned

- `OperationalCase` remains the durable source of truth. WorkItem continues to be explicitly documented as a projection layer in `app/brain/work_items.py`, not a competing task store.
- Current WorkItem projection has important Atlassian-like primitives: project key derivation, project projection, issue-type mapping from case type, status categories, workflow/status definitions, transition lists, work item IDs, and priority brackets.
- `operational_case_priority_definitions()`, `priority_bracket_for_score()`, and `case_priority_bracket()` now provide a canonical low/medium/high scheme, closing the previous priority drift gap.
- JQL-lite remains intentionally bounded: in-memory filtering, no SQL translation, max length/clause/IN limits, allowlisted fields/operators, safe errors, and redacted outputs.
- Built-in views are read-only projections over case state; this matches the correct Atlassian pattern for MVP filters without creating saved-filter persistence prematurely.

### Gaps / concerns

1. **WorkItem is still projection-only.** This is correct for MVP but still not a full Jira-grade work-management aggregate. There are no durable Project, IssueTypeScheme, WorkflowScheme, saved filter, rank, watcher, comment table, issue-link, field-configuration, or permission-scheme records.
2. **Query-field semantics are still local on HEAD.** `operator_views.py` owns `_FIELD_SPECS` locally. This is safe but becomes drift-prone as search analytics and dashboards add fields. Branch `10ed711` fixes this by moving query field definitions into WorkItem semantics.
3. **JQL-lite is not a platform query engine.** It lacks saved filters, cursor pagination, permissioned fields, query audit, and versioned grammar. Continue presenting it as operator-view filtering until those primitives exist.
4. **Service/SLA additions need nesting.** Service-management SLA/status fields should remain nested service projections; canonical OperationalCase status categories should remain exactly `to_do`, `in_progress`, and `done`.

### ARB requirement

Merge the WorkItem query-field registry before broad `search-analytics` or `operator-surfaces` work. Every new JQL/view/facet field must be one of:

- a WorkItem/OperationalCase projection field from the WorkItem query registry;
- a registered semantic metric from `MetricRegistry`;
- a route-local display label that cannot be mistaken for business truth.

## 2. Semantic registry as canonical source of truth / metric drift

### Aligned

- `app/brain/semantics/metric_registry.py` remains the canonical source for business measurements: immutable metric definitions, alias resolution, allowed sources, units, aggregation, evidence requirements, PII class, and case/report allow flags.
- `CASE_FAMILY_METRICS` is a read-only `MappingProxyType`; owner-facing/detectable case family behavior derives from registry-backed mappings rather than catalog prose alone.
- Operational case evidence resolves aliases to canonical `metric_key` values and preserves source aliases only as metadata.
- Connector registry validation uses the semantic registry to check emitted metric families/objects; this is the right anti-drift seam.
- Current tests cover connector registry and metric validation contracts; full suite is green at `1323 passed`.

### Gaps / concerns

1. **Case-family vocabulary still exists in multiple places.** `OperationalCaseType`, `CASE_FAMILY_METRICS`, docs catalogs, and action-key policies must stay in lockstep. `channel_mix_shift` remains correctly deferred because it is not owner-facing in `CASE_FAMILY_METRICS`.
2. **Analytics/facets are not metrics.** Fields like `priority_bracket`, `source_connector`, `entity.kind`, `degraded`, evidence counts, freshness state, and queue totals are useful projection fields but should not be added to templates as business metric keys.
3. **Future tenant overrides must not bypass registry validation.** Metric registry is Python-code canonical today; if/when moved to persisted config, the same strict validation/evidence rules must remain.

### ARB rule

Any new owner-facing numeric/business claim must answer: **Which canonical metric key and evidence snapshot back this?** If no metric/evidence exists, the field may only be rendered as a projection counter or omitted.

## 3. Connector platform: adapter / service / storage separation

### Aligned

- `connector_registry.py` owns connector specs, adapter module/factory, capabilities, required config fields, secret refs, legacy secret config metadata, executor metadata, health metadata, rate-limit metadata, scopes, lifecycle, and emitted metric families.
- The resolved-secret seam is now baseline: connector factory params can use `resolved_secret_param`, and current secret-bearing Tiendanube/MercadoLibre/WooCommerce adapter kwargs should be execution-scoped rather than durable public params.
- Adapter validation is declarative through registry metadata and `validate_daily_report_adapter()`.
- Registry/runtime/ledger/semantic validation remains the desired execution path; there is no observed Tiendanube/WhatsApp shortcut in current HEAD.

### Gaps / concerns

1. **Connector platform branch is broad.** `codex/connector-platform` is strategically aligned but touches config, registry, runtime, execution ledger, redaction, semantic registry, docs, and many tests. It should be reviewed as a core-platform merge, not a small surface patch.
2. **Durable connector health/rate-limit enforcement is still limited.** Metadata/classification exists, but full connector instance storage, health history, rate-limit counters/backoff state, and provisioning audit remain future work.
3. **Legacy adapters still accept raw token kwargs.** This is acceptable only as an ephemeral execution detail after secret resolution; raw values must never appear in durable connector config, compiled runtime serialization, run ledger artifacts, docs, examples, or operator responses.

### ARB recommendation

Use the newer `codex/connector-platform @ bbd4f52` as the candidate source after confirming it supersedes `codex/eng-factory-connector-platform-reconcile-20260606`. Required gates: connector registry contract tests, compiled runtime tests, redaction invariant tests, Google Sheets/CSV/Tiendanube compatibility tests, and a diff review for any route-local connector shortcuts.

## 4. Workflow automation: idempotency, approval gates, audit

### Aligned

- Current internal HTTP case-action route now requires `X-Idempotency-Key` before mutation.
- `apply_case_action_with_idempotency()` reserves a `WorkflowActionLedgerRecord` with `pending_execution` before applying the manual mutation, marks it `executed` after success, marks it `failed` on exception, and returns `skipped_duplicate` for safe replays.
- Invalid, blank, oversized, unsupported-character, and secret-shaped idempotency keys are rejected.
- Manual actions validate action keys against the registered action catalog and disabled-boundary list.
- Workflow action ledger has uniqueness on `(business_id, idempotency_key)` and tracks source, action, actor, params, approval, and execution state.

### Gaps / concerns

1. **The service helper still allows direct non-idempotent mutation.** `apply_case_action_with_idempotency(..., idempotency_key=None)` still falls back to `apply_case_action()`. This may be acceptable for internal/non-HTTP callers during migration, but every transport mutation boundary should require idempotency.
2. **Approval decision audit must be durable before execution.** Workflow branch returns/project audit events, but production automation should append approval/rejection/cancellation decisions to `operator_audit_events` or a workflow audit table before any executor consumes approved actions.
3. **External side effects must remain disabled/fail-closed.** No branch should enable broad action execution unless action catalog, approval state, ledger state, actor identity, provider idempotency, retry/failure semantics, and redacted audit linkage all agree.
4. **Idempotency keys are stored raw after validation.** Validation rejects secret-shaped values, which is good. Later, consider storing a deterministic hash lookup key plus redacted display value for defense-in-depth.

### ARB recommendation

Decompose `codex/workflow-automation`; merge approval/execution-gate invariants before new trigger conditions or surfaces. Keep `side_effects_executed = 0` for projections until durable audit and executor gates are proven.

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### Aligned

- Internal API uses bearer-token authentication with constant-time comparison and fail-closed behavior when token config is absent.
- Operator roles/permissions are explicit (`viewer`, `operator`, `admin`) with separate `internal:read`, `case:action`, and `operator_audit:read` permissions.
- Route business scope is enforced when `X-Orvo-Businesses` is supplied; audit reads use redacted display IDs plus deterministic business scope keys.
- Internal success/error envelopes include request IDs, business IDs, and redaction flags; current HEAD redacts error messages and request IDs/business IDs when secret-shaped.
- Failed auth/authorization and denied action paths append best-effort redacted audit events.
- Secret boundaries are stronger after resolved-secret connector bindings.

### Gaps / concerns

1. **RBAC is still coarse and header-based.** This is acceptable for internal MVP, but a platform-grade control plane needs per-operator identity, rotated credentials, service principals, and route-level permission matrix tests for every read/write/admin endpoint.
2. **Actor refs are caller-controlled.** Current `build_internal_operator_principal()` and `normalize_operator_actor()` do not collapse secret-shaped actor refs before timeline/ledger use. `codex/trust-admin-security` appears to address this with `safe_internal_operator_actor_ref()`; cherry-pick/rebase that behavior.
3. **Error code sanitization is incomplete on current HEAD.** Error messages are redacted, but `_internal_error()` still echoes `code`. Codes are normally static, but trust branch's `_safe_internal_error_code()` is a useful hardening step.
4. **Audit append failures are best-effort.** Failing closed on auth is correct, but production should emit a safe operational counter/signal if audit writes fail repeatedly.
5. **Legacy token-scoped access remains when no business-grant header is supplied.** This preserves compatibility but should be tightened before multi-tenant/live admin use.

### ARB recommendation

Rebase `codex/trust-admin-security` and cherry-pick the small hardening deltas: safe actor refs before durable timelines/ledgers, bounded audit identifiers, and safe error-code handling. Add route-level permission matrix tests as the next Trust/Admin/Security invariant.
