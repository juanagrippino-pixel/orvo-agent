## Executive verdict

The platform is moving in the right direction for an Atlassian/Jira-like D2C operations control plane: current code keeps `OperationalCase` as the durable issue/work source of truth, derives WorkItem/JQL/operator surfaces as projections, routes connector execution through registry/runtime/ledger metadata, and has increasingly strong redaction/RBAC/audit guards.

However, the recent branch set shows two recurring risks:

1. **Surface proliferation ahead of consolidation.** Operator/search/analytics branches add many read-only endpoints and saved-view-like projections. They generally stay source-of-truth aligned, but the surface area is growing faster than the contract taxonomy.
2. **Semantic promotion drift.** `channel_mix_shift` appears in OperationalCase literals, entity scopes, dedupe helpers, service-management mappings, and action mappings, but `CASE_FAMILY_METRICS` intentionally excludes it; this currently prevents deterministic detection/owner-facing promotion. That is acceptable as a deferral mechanism, but it must remain explicit and tested so a surface does not imply the family is promoted.

Recommended merge posture: merge the small redaction/docs guards first, then rebase and selectively merge operator/search/service/workflow branches only where they remain pure projections over canonical cases, metric registry, connector registry, and workflow ledgers.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### What is aligned

- `OperationalCase` is the canonical durable issue object. Statuses are centralized as `open`, `acknowledged`, `in_progress`, `resolved`, `dismissed` with canonical status categories `to_do`, `in_progress`, `done`.
- `work_items.py` correctly treats WorkItem as an Atlassian/Jira-like projection, not a separate task store. It derives:
  - project key from `business_id` with deterministic normalization/hash protection;
  - issue type from case family;
  - workflow/status definitions from `operational_case_status_transitions()`;
  - `work_item_id` from project key + canonical `case_id`.
- `operator_views.py` implements a bounded JQL-lite parser, never SQL translation. It allowlists fields/operators, limits query length/clauses/IN values, and reads cases by `business_id` first.
- Recent search additions add useful Jira-like fields (`work_item_id`, `assigned`, `actionable`, `freshness_state`) while resolving them through canonical case/work-item/evidence helpers.
- System reopen logic in `codex/work-management` is architecturally valid if kept separate from operator transitions: recurrence-driven reopen after terminal state should be detection/system-only and auditable, not a manual operator transition.

### Gaps / risks

- **No persisted project/issue/workflow scheme registry yet.** Current project/issue/workflow objects are deterministic projections. That is acceptable for Phase A, but admin surfaces must not imply tenant-configurable Jira projects/workflows until an explicit registry/schema exists.
- **Service-management status vocabulary must remain nested.** `codex/service-management` uses owner-friendly codes like `waiting_owner` and `waiting_external`, mapped to `in_progress` category. This is good if exposed as `owner_status`/`service_status`; it would be a problem if these become canonical `OperationalCase.status` or `status_category` values.
- **Operator-surface branch is too broad.** `codex/operator-surfaces` adds many recent-* endpoints and duplicates very similar projection patterns. The logic is generally correct/read-only, but should be split or consolidated into reusable activity-query helpers before merge.
- **Wildcard import coupling is spreading.** Several operator API modules rely on `from .common import *` / `from app.brain.operator_api import *`. This increases accidental symbol coupling as surfaces grow. It is not an immediate blocker, but it is a maintainability risk for a Jira-like platform surface.

### Recommendation

Keep `OperationalCase` + projected WorkItem for now. Do not introduce a separate WorkItem persistence table. Before claiming full Atlassian-style projects/workflows, add a formal project/workflow scheme contract or keep documentation explicit that they are deterministic projections.

## 2. Semantic registry as canonical source of truth

### What is aligned

- `MetricRegistry` is strong: canonical keys, aliases, units, allowed sources, aggregation, freshness/evidence flags, PII class, source-envelope validation, family-envelope validation, value-kind validation, evidence validation, and currency validation all live in `app/brain/semantics/metric_registry.py`.
- `OperationalCase` detections use `CASE_FAMILY_METRICS` to determine detectable/owner-facing case families:
  - `DETECTABLE_OPERATIONAL_CASE_TYPES = frozenset(CASE_FAMILY_METRICS)`
  - `OWNER_FACING_OPERATIONAL_CASE_TYPES = frozenset(CASE_FAMILY_METRICS)`
- Case evidence metrics are filtered through `registry.try_resolve_key()`, `definition.case_allowed`, source evidence, and case-family metric allowlists.
- Connector specs validate emitted metric keys/families through the semantic registry, reducing adapter-driven metric drift.

### Gaps / risks

- **`channel_mix_shift` is intentionally unpromoted but present in many places.** It exists in `OperationalCaseType`, dedupe/entity-scope helpers, service-management record-type mapping, and action/service surface logic. But it is absent from `CASE_FAMILY_METRICS`, so detections are suppressed by `_case_type_for_insight()` and owner-facing projection is blocked. This is good as a guard, but it must remain explicit; otherwise future contributors may think the case family is live.
- **Metric validation remains advisory in some runtime/case paths.** `_metric_registry_metadata(report)` uses `validate_metrics(..., strict=False)` and attaches issues as metadata. This is acceptable while adapters are transitional, but promotion gates should fail or suppress owner-facing cases when unknown/disallowed metrics drive claims.
- **Operator analytics are not semantic metrics.** New aging/latency/throughput dashboards are workflow analytics over cases/timelines, not registered business metrics. That is okay if documented. Do not mix them into the semantic metric registry unless they become productized KPIs with units/freshness/evidence policy.

### Recommendation

Create/keep an invariant test that verifies every owner-facing/detectable case family is in `CASE_FAMILY_METRICS`, and every unpromoted case family (currently `channel_mix_shift`) stays hidden from detection/owner surfaces until registry metrics are added. Promote `channel_mix_shift` only by adding canonical semantic keys/families first, then updating detections/actions/surfaces.

## 3. Connector platform separation: adapter / service / storage

### What is aligned

- `connector_registry.py` cleanly separates connector metadata from adapter implementation:
  - static `ConnectorSpec` / `ConnectorExecutorMetadata` describe factories and allowed params;
  - adapter factories are loaded through registry metadata;
  - compiled runtime persists safe connector metadata and strips raw legacy secrets;
  - run/execution ledger records connector outcomes.
- `codex/connector-platform` adds `emitted_event_families` (`connector.execution`, `connector.health`) to registry/runtime/ledger metadata. This is additive and correctly says adapters must not claim event families until runtime/ledger records them.
- Secret boundaries are visible: required secret refs are control-plane handles, while legacy inline secret params remain transitional execution compatibility.
- Connector emitted metrics are certified against registry source/family/evidence/value/currency envelopes.

### Gaps / risks

- **Runtime secret-ref resolution is still transitional.** Specs model secret refs, but adapters still need raw execution tokens supplied somewhere. That bridge must remain inside runtime/secret resolution, not operator surfaces or persisted metadata.
- **No connector storage/provisioning service yet.** The registry is static code. That is acceptable for early platform core, but admin/self-service connector management should not be positioned as complete until connector instances, health history, secret refs, and provisioning audits have first-class storage/service contracts.
- **External action providers must stay sidecar tools.** `external_actions.py` correctly reserves core toolkits (`tiendanube`, `whatsapp`, etc.) so Composio/Pipedream-style providers cannot bypass core connectors. The new identifier validation branch strengthens this boundary.

### Recommendation

Merge connector event-family metadata after rebase/test. Keep the next connector-platform milestone focused on secret-ref resolution and connector instance/audit storage, not broad connector marketplace claims.

## 4. Workflow automation: idempotency, approval gates, audit

### What is aligned

- Workflow planning is dry-run/projection-first. `simulate_case_workflow()` returns `side_effects_executed = 0`.
- Idempotency keys are deterministic and redacted-param based via `make_workflow_idempotency_key()`.
- `WorkflowActionLedgerStore.record_planned_action()` provides canonical planning records and duplicate detection by idempotency key.
- Approval-required actions are blocked (`blocked_approval_required`) before execution.
- `external_actions.py` enforces:
  - allowed toolkit/action pairs;
  - reserved core toolkit rejection;
  - run-ledger scope checks;
  - write approval linkage;
  - idempotency checks before provider calls;
  - redacted payload/response metadata.
- `codex/workflow-automation` adds a read-only audit projection over workflow action/approval records and event-trigger matching that prevents ledger writes on trigger mismatch.

### Gaps / risks

- **Approved workflow actions still should not execute broadly.** The planning/approval boundary is good, but a production executor still needs actor identity, retry/failure semantics, execution attempts, provider-specific idempotency proof, RBAC, and operator audit linkage before enabling side effects.
- **Audit taxonomy naming needs normalization.** `workflow_action_audit.py` event names (`workflow_action_planned`, `workflow_approval_requested`, etc.) are understandable, but should be cross-checked against `operator_audit`/internal API event naming before becoming durable external contract.
- **External action branch should be merged soon.** Toolkit/action regex validation prevents identifier injection or secret-shaped identifiers from being sent to provider clients/ledgers.

### Recommendation

Merge the external-action redaction/identifier guard first. Merge workflow audit projection after a taxonomy review. Do not enable real side effects beyond the existing guarded external action boundary until the executor contract lands.

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### What is aligned

- Internal API authorization fails closed when `ORVO_INTERNAL_OPERATOR_TOKEN` is absent or invalid.
- Role permissions are centralized in `operator_auth.py`; business scoping is explicit through allowed-business headers.
- Operator action endpoints enforce `CASE_ACTION_PERMISSION` and record denied actions.
- `codex/trust-admin-security` improves:
  - audit of authentication denials without storing raw Authorization headers;
  - authorization denial audit for operator audit export route;
  - redaction of malformed/unknown roles and actor/request/target identifiers.
- Run/operator projections defensively redact secret refs at the API boundary.
- Owner-facing projections increasingly filter to evidence-backed cases and redact action/case data.

### Gaps / risks

- **Audit store redacts identifiers before persistence.** This is good for secret-adjacent values, but if a `business_id` is redacted at write time, later `WHERE business_id = ?` queries with the original value may not find it. Usually business IDs are safe and unchanged, but the branch should include a test for secret-shaped business IDs or explicitly decide that such tenants are unsupported/sanitized at config time.
- **RBAC is header-token based.** This is acceptable for internal Phase A, but admin/security positioning should not imply full user management/session auth until backed by identity provider integration, durable users/groups/roles, and audit exports.
- **Surface growth increases audit obligations.** Every new endpoint added by operator/search/service branches must use the common internal auth wrapper and denial audit path where applicable.

### Recommendation

Merge trust/admin-security after rebase/test, with one extra check around redacted `business_id` lookup behavior. Keep admin claims scoped to internal-token/header-principal RBAC until a real identity model exists.
