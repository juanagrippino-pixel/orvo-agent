## Executive verdict

Current `feat/orvo-brain-control-plane` is **merge-ready as the integration baseline**. Since the earlier 2026-06-11 ARB report, the most important prior architecture concern has been addressed: metric registration no longer automatically means owner-facing promotion. Current code separates:

- `DETECTABLE_OPERATIONAL_CASE_TYPES` from `CASE_FAMILY_METRICS`;
- explicit `OWNER_FACING_OPERATIONAL_CASE_TYPES` (`sales_drop`, `stockout_risk`, `data_stale`);
- `READINESS_GATED_OPERATIONAL_CASE_TYPES` for registered-but-not-owner-facing families;
- WorkItem `release_state` values: `promoted`, `readiness_gated`, `deferred`, `internal_only`.

Other positive deltas now on the baseline:

1. **Atlassian/Jira-like work management is better aligned.** `OperationalCase` remains the issue source of truth; WorkItem is projection/registry only. Status categories, issue types, release state, project keys, workflow definitions, priority brackets, and JQL-lite/facet fields are centralized in `app/brain/work_items.py` rather than scattered across endpoints.
2. **Owner/worker actor taxonomy landed.** `ActorType` now includes `system`, `operator`, `owner`, and `worker`, closing a gap from the earlier report and preparing timelines for owner replies and autonomous-worker actions.
3. **Connector failure honesty improved.** The connector-failure-to-`data_stale` integration is now in the baseline, so degraded connector states can create/update cases rather than letting reports imply unsupported certainty.
4. **Operator inspection improved without bypassing runtime.** Internal runtime compile preview and connector readiness endpoints are read-only projections over config, registry, and ledger state; they do not execute connectors or resolve raw secrets.
5. **Run-ledger partial behavior is protected.** Recent baseline work records partial guard integration, and the full suite passes.

Remaining strategic risks are now mostly about **surface breadth and policy hardening**, not core source-of-truth violations:

- Release/readiness state is correct but still hard-coded in code constants; before adding more families or module tiers, promote this into an explicit case-family readiness/promotion policy registry with docs and tests.
- Operator surfaces and search analytics branches remain valuable but too endpoint-heavy; merge primitives into WorkItem/JQL/facet/view registries, not bespoke route bundles.
- Connector platform branches are strategically aligned but broad; rebase and merge contract/certification slices selectively.
- Internal auth/RBAC is stronger, but legacy defaults (`role=None -> operator`, absent business grants treated as legacy token-scoped) remain a blocker for external Admin/SaaS exposure.
- La Pyme/Tango OS-scope docs are directionally accepted, but code branches must not turn ARCA/treasury/customer-attention readiness into unsupported owner-facing claims before connector/evidence gates exist.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### Alignment

The current baseline follows the desired Atlassian/Jira pattern:

- `OperationalCase` remains the durable issue/workflow object and source of truth.
- `app/brain/work_items.py` is explicitly a projection/registry layer, not a new store.
- Project keys derive from route/business scope (`project_key_for_business`) rather than user-supplied JQL project values.
- Issue-type definitions expose `release_state`, now separated from metric registration.
- Workflow definitions expose manual transitions and system-only reopen transitions separately.
- Status categories remain the Jira-like canonical set: `to_do`, `in_progress`, `done`.
- Query, sort, and facet fields are centralized via `WorkItemQueryFieldDefinition`, `work_item_query_field_spec()`, `allowed_work_item_query_sort_fields()`, and `allowed_work_item_facet_fields()`.
- `ActorType` now includes `owner` and `worker`, so timelines can support future owner/operator/autonomous-worker activity without overloading `operator`.

### Gaps / risks

1. **Readiness policy is correct but not yet a first-class policy registry.**
   - Current constants are good enough for Phase A.
   - Before promoting `fulfillment_backlog`, `spend_without_orders`, or `unanswered_conversations`, create an explicit case-family readiness/promotion registry with promotion prerequisites, not another hard-coded set.

2. **Work-management branches are broad.**
   - SLA, evidence lineage, transition-boundary, and timestamp invariants are valuable.
   - They must stay as fields/projections/timeline invariants over `OperationalCase`, not become a separate service-ticket lifecycle.

3. **Endpoint proliferation can undermine Jira-like coherence.**
   - A control plane should feel like projects + issues + JQL/views + dashboards, not dozens of independent bespoke endpoints.
   - Favor view definitions, facets, and query registries over one route per dashboard card.

### ARB call

- **Baseline:** aligned.
- **Merge priority:** small WorkItem invariants and query/facet registry additions.
- **No-go:** parallel task/workflow stores or lifecycle state owned by WhatsApp/report text.

## 2. Semantic registry canonicality / metric drift

### Alignment

The semantic registry remains the canonical source of truth for business metrics:

- `app/brain/semantics/metric_registry.py` defines canonical keys, aliases, units, allowed sources, aggregation, report/case eligibility, evidence requirements, and PII classes.
- `CASE_FAMILY_METRICS` is still the anti-drift mapping from case families to canonical metrics.
- `OperationalCase` detection eligibility uses `DETECTABLE_OPERATIONAL_CASE_TYPES = CASE_FAMILY_METRICS` while owner-facing eligibility is explicitly narrower.
- Readiness-gated families can now be detected/internal without being projected into owner-facing surfaces.
- Metric validation covers unknown keys, alias resolution, source/family envelope mismatches, evidence requirements, value-kind issues, and money/currency requirements.

### Gaps / risks

1. **Metric registration is still being asked to carry too much policy.**
   - It should remain the semantic/evidence source of truth.
   - Release readiness should live in an adjacent policy layer that can represent source readiness, structured connector availability, SLA/business-hours policy, resolver ownership, stale suppression, and redaction/PII gates.

2. **Manual/sample compatibility remains a careful boundary.**
   - Support/conversation metrics accept `sample` and `google_sheets` compatibility in places.
   - That must not be interpreted as production readiness for a WhatsApp inbox/backlog module.

3. **La Pyme OS expansion needs semantic discipline.**
   - ARCA readiness, treasury/reporting, and customer-attention modules can be setup/readiness projections now.
   - They cannot emit owner-facing metrics/cases until canonical metrics, connectors, evidence, and readiness gates exist.

### ARB call

- **Baseline:** aligned and improved since prior report.
- **Merge gate:** no new owner-facing metric, alias, connector emitted family, case dependency, or PyME module claim outside the semantic registry + promotion policy + tests.

## 3. Connector platform: adapter / service / storage separation

### Alignment

The current connector platform is moving correctly:

- `connector_registry.py` owns connector type, capabilities, params, secret requirements, emitted metric/event families, executor metadata, health/rate-limit/scope/lifecycle metadata, and validation helpers.
- `runtime.py` compiles runtime metadata from config/registry without exposing raw secret values.
- Internal connector readiness uses config + registry + last run-ledger outcomes and does not execute connectors or resolve raw secrets.
- Connector failures are now represented as stale/degraded cases, improving degraded-mode honesty.
- `run_ledger.py` and related tests protect redaction and terminal/partial run status behavior.

### Gaps / risks

1. **Connector-platform branch is high-value but conflict-prone.**
   - It touches config, registry, runtime, runner, execution ledger, metric validation, and redaction.
   - Merge it in certification slices: secret scopes, executor metadata, metric/event family certification, registry filtering, health policy metadata.

2. **Readiness is not live health.**
   - Current readiness endpoint is metadata + latest recorded outcome, which is honest.
   - Do not market live self-service connector health/provisioning until health-check execution, provisioning audit, retries, and scoped credentials are implemented.

3. **Legacy inline secrets remain execution-scoped transitional inputs.**
   - This remains acceptable only if raw values never enter durable runtime serialization, ledger artifacts, operator API responses, audit events, docs, or examples.

### ARB call

- **Baseline:** aligned for Phase A.
- **Merge priority:** connector-platform certification slices and dispatch idempotency redaction tests.
- **No-go:** direct connector-to-report/case shortcuts that bypass registry, runtime, ledger, metric registry, or evidence snapshots.

## 4. Workflow automation: idempotency, approval gates, audit

### Alignment

The current workflow automation posture remains safe:

- Manual case actions require idempotency and catalog-defined action keys.
- Terminal transitions require reasons.
- Workflow automation is simulation/projection-oriented, not a side-effect executor.
- `list_workflow_execution_queue()` only projects catalog-defined approval-required actions with `approval_state=approved`, `execution_state=pending_execution`, and a matching approved approval-request object.
- Queue projections explicitly return `execution_enabled = False`, `executor_state = not_implemented`, and `side_effects_executed = 0`.

### Gaps / risks

1. **Approved queue must not become execution by implication.**
   - A future executor requires an execution-attempt ledger, provider idempotency proof, RBAC/action-scope checks, retries, redacted provider response audit, and failure semantics.

2. **Automation conditions should use WorkItem fields.**
   - Assignee and priority-bracket conditions are fine if they use canonical WorkItem/case fields and remain simulation/projection-only.

3. **External side effects need repeated red-team tests.**
   - The action-catalog side-effect guard is integrated; keep adding invariants before any real external execution path.

### ARB call

- **Baseline:** aligned.
- **Merge:** `codex/workflow-automation` or the smaller `workflow-priority-bracket` subset after rebase, as long as no side-effect execution is introduced.
- **No-go:** executable external automation without approval, idempotency, RBAC, and audit attempt ledger.

## 5. Trust / Admin / Security: RBAC, audit, secret boundaries

### Alignment

Trust posture is strong for internal/operator use:

- Roles and permissions are centralized in `operator_auth.py`: `viewer`, `operator`, `admin`.
- Case mutation and audit-read permissions are separated.
- Global/cross-business surfaces require explicit global business grant.
- Internal envelopes, audit events, connector readiness projections, runtime previews, run ledger artifacts, and evidence models apply defensive redaction.
- Authentication/authorization denials are audited without raw bearer tokens.
- Operator audit storage and delivery-status routes have business/global scope hardening.

### Gaps / risks

1. **Legacy auth compatibility is still not external SaaS-ready.**
   - `normalize_operator_role(None)` defaults to `operator`.
   - absent business allowlist means legacy token-scoped access on tenant routes.
   - This must be removed or explicitly environment-gated before customer-facing Admin.

2. **Trust branch overlap is high.**
   - `codex/trust-admin-security` is directionally correct but overlaps with many landed controls.
   - Rebase and merge unique controls only: bounded audit exports, cookie/header credential redaction, taxonomy label hardening, stricter idempotency key checks, and any missing denial/success audit records.

3. **Audit-outage policy remains a future production decision.**
   - Current best-effort audit with fail-closed auth is acceptable internally.
   - External privileged mutations need a policy: block, queue audit, or mark degraded when audit sink is unavailable.

### ARB call

- **Baseline:** internally strong.
- **Merge priority:** unique trust/security tests and hardening after rebase.
- **Release blocker:** no external Admin surface while legacy implicit role/business grants remain enabled.

## Strategic recommendations

1. **Promote readiness policy into a first-class registry.** Current hard-coded owner-facing/readiness-gated split fixed the immediate bug; the next scalable step is a policy registry that pairs case families with promotion prerequisites.
2. **Merge primitives before bundles.** Favor WorkItem/JQL/facet fields, connector certifications, redaction invariants, and audit guards. Split broad operator/search/service bundles.
3. **Keep La Pyme OS expansion as readiness/status projection until evidence exists.** ARCA, treasury, Mercado Pago, WhatsApp attention, and fulfillment lanes should show setup/readiness, not unsupported operational claims.
4. **Treat connector readiness as an inspection surface, not a live health guarantee.** The current endpoint is honest; future live checks need audited execution and rate-limit policy.
5. **Preserve WhatsApp as projection/channel only.** The app/operator console remains the control surface; WhatsApp briefs should reference cases/evidence and never own workflow state.
6. **Do not dilute the Tiendanube D2C wedge with platform breadth.** Connector breadth, gateway/service catalog, and service-management concepts are useful only when they deepen the first sellable control-plane slice.

- **Current baseline:** merge-ready and test-verified.
