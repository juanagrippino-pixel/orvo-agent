## Executive verdict

The codebase is still directionally aligned with the accepted product/architecture split: sell a narrow D2C ecommerce control plane; build a durable Atlassian-like platform core. Recent landed work mostly strengthens the architecture: JQL-lite parsing hardening, case/redaction invariants, operator auth-denial audit, delivery-status denial audit, internal success-envelope redaction, and idempotency replay tests all reinforce deterministic control-plane behavior.

The main architectural risk has shifted from “missing platform primitives” to “too many overlapping surface/projection branches.” Core primitives are credible, but operator endpoints are multiplying faster than the WorkItem/JQL/view registry abstraction. This is the same strategic danger Atlassian avoids by making projects, issue types, workflows, fields, JQL, dashboards, and reports composable primitives rather than one endpoint per widget.

Top ARB calls:

1. **OperationalCase / WorkItem is aligned, but merge the work-management workflow clarification.** Current main has Jira-like status categories and WorkItem projections, but the exported workflow table does not explicitly expose system reopen transitions from terminal states even though deterministic detections can reopen via `case_reopened`.
2. **Semantic registry remains canonical.** `CASE_FAMILY_METRICS` gates detectable/owner-facing case families. `unanswered_conversations` has canonical support metrics, but should not become owner-facing until a real WhatsApp/support connector emits evidence under registry rules.
3. **Workflow automation needs one guard before future execution.** Current main’s execution queue is no-side-effect, but it does not require a matching approved approval-request object before projecting `pending_execution`. `codex/workflow-automation` fixes that pattern.
4. **Trust/Admin is improving but not production SaaS-ready.** Legacy default role=`operator` and `allowed_businesses=None` token-scoped behavior are acceptable for internal migration only. External Admin launch must require explicit role and business claims.
5. **Endpoint proliferation is now the largest Atlassian-pattern risk.** Current main and `codex/operator-surfaces` expose many summary/latency/stagnation/recent routes. Prefer a generic view/facet/query contract over adding more bespoke routes.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### What is aligned

Current main now has the essential Jira-like shape:

- `OperationalCase` remains the durable issue/workflow object, with WhatsApp/report/operator surfaces as projections.
- Status categories exist: `to_do`, `in_progress`, `done`.
- Lifecycle states are deterministic: `open`, `acknowledged`, `in_progress`, `resolved`, `dismissed`.
- `WorkItem` is correctly additive: project key, issue type, workflow/status category, priority bracket, assignee, timestamps, and case id are projected from `OperationalCase`.
- JQL-lite is allowlisted through `WorkItemQueryFieldDefinition`; user input is parsed in memory rather than translated to SQL.
- Recent `jql-empty-in` hardening correctly rejects empty `IN` clauses.

### Gaps / risks

1. **System reopen transitions are implicit in main.**
   - `OperationalCaseStore.upsert_detection()` reopens resolved/dismissed cases when deterministic evidence recurs.
   - But `_CASE_STATUS_TRANSITIONS` exposes `resolved: set()` and `dismissed: set()` to workflow metadata.
   - This is defensible if the table represents *manual/operator transitions only*, but the API should say that explicitly. `codex/work-management` appears to add clearer system-reopen semantics and should be prioritized.

2. **Actor taxonomy is narrower in main than the contract.**
   - The contract allows `system`, `operator`, `owner`, `worker`.
   - Current main’s `ActorType` is only `system | operator`.
   - For a sellable control plane, owner replies and autonomous worker events should not be squeezed into ambiguous operator/system labels.

3. **Deferred case families need release-state metadata.**
   - `OperationalCaseType` includes `channel_mix_shift`, but `OWNER_FACING_OPERATIONAL_CASE_TYPES` is gated by `CASE_FAMILY_METRICS`, so it is not owner-facing in main.
   - WorkItem issue-type definitions currently expose all case types without an explicit `promoted/deferred` field.
   - Add release-state metadata so internal surfaces can distinguish “known type but not owner-facing/detectable yet.”

### ARB recommendation

- Merge `codex/work-management` after rebase.
- Add explicit workflow metadata separation:
  - manual/operator transitions;
  - deterministic system reopen transitions;
  - terminal states.
- Add issue-type release state: `promoted`, `deferred`, `internal_only`.

## 2. Semantic registry as canonical source of truth

### What is aligned

The semantic registry is still the right source of truth:

- `CASE_FAMILY_METRICS` gates `DETECTABLE_OPERATIONAL_CASE_TYPES` and `OWNER_FACING_OPERATIONAL_CASE_TYPES`.
- Canonical metrics cover current D2C families: commerce orders/revenue/inventory, fulfillment, support conversations, ads spend, runtime freshness, connector status.
- Legacy aliases resolve explicitly; unknown metrics produce typed validation issues/errors rather than silent drift.
- Connector emitted metrics are checked against allowed source and declared family envelopes.
- Current full suite and contracts/invariants pass.

Recent `research: unanswered whatsapp conversations` is strategically aligned because the metric registry already has:

- `support.conversations.unanswered_count`
- `support.conversations.oldest_unanswered_age_minutes`
- `unanswered_conversations` case-family mapping

But this should remain a readiness/research artifact until a real WhatsApp/support connector emits evidence with freshness, source, and PII boundaries.

### Gaps / risks

1. **`channel_mix_shift` remains a recurring footgun.**
   - It is in the enum/catalog but intentionally absent from `CASE_FAMILY_METRICS`.
   - `codex/service-management` maps it to a Service Management `problem` record type. That is acceptable only as an internal/deferred projection; it must not make `channel_mix_shift` owner-facing by accident.

2. **Operator analytics are not business metrics but still need registry discipline.**
   - Aging/latency/stagnation endpoints compute workflow KPIs from case timestamps. They should not be forced into the business metric registry, but they should be governed by the WorkItem field/view/facet registry.
   - Otherwise “metric drift” can reappear as “operator KPI drift.”

3. **Advisory validation needs operational visibility.**
   - Advisory metric issues are useful, but passive metadata can hide connector drift unless surfaced in CI/operator health.

### ARB recommendation

- Keep `CASE_FAMILY_METRICS` as the release gate for owner-facing/detectable case families.
- Add `release_state` to case-family/issue-type projections.
- Add a small CI or operator-health report for unknown/advisory metric issues by connector.
- Do not promote `unanswered_conversations` owner-facing until WhatsApp/support evidence and stale suppression tests exist.

## 3. Connector platform: adapter / service / storage separation

### What is aligned

Current main and the local `codex/connector-platform` branch preserve the correct separation:

- `connector_registry.py` owns connector specs, capabilities, required config, required secret refs, health metadata, rate limits, executor metadata, and validation.
- Adapter factories are invoked through registry metadata rather than route-level hardcoding.
- Legacy inline secrets are explicitly marked transitional; durable config should use `secret_refs`.
- Metric validation composes registry checks: unknown key, disallowed source, undeclared family, evidence required, source mismatch, value-kind mismatch, money currency missing.
- `redaction.py` preserves safe `secret://` refs while redacting raw values.

### Gaps / risks

1. **Two connector-platform branches exist with very different risk profiles.**
   - Local `codex/connector-platform`: `5 / 13`, focused suite passed, appears narrow enough to rebase and review.
   - `origin/codex/connector-platform`: `87 / 72`, broad/stale; do not direct-merge.

2. **Execution still has transitional inline secret paths.**
   - This is acceptable while existing adapters require raw tokens at execution time.
   - It remains a hard boundary: raw secrets may exist only on execution-scoped copies, never in compiled runtime metadata, run ledger, audit, operator API, docs, or examples.

3. **Health is still partly metadata-first.**
   - `ConnectorHealthMetadata(readiness_check="metadata_only")` is a good contract placeholder.
   - Self-service connector claims require real readiness probes and typed health state persistence before buyer-facing/admin use.

### ARB recommendation

- Rebase and consider merging local `codex/connector-platform` if diff remains scoped.
- Close or supersede the stale remote connector-platform branch to avoid accidental broad merge.
- Add a “no raw secret in compiled/runtime/ledger/operator/audit” invariant for every new connector.

## 4. Workflow automation: idempotency, approval gates, audit

### What is aligned

Current main is safe-by-default:

- Workflow actions are ledgered.
- Idempotency keys are durable and business-scoped.
- Approval queue is a projection with zero side effects.
- Execution queue declares `execution_enabled: False`, `executor_state: not_implemented`, and `side_effects_executed: 0`.
- Current and branch tests cover failed idempotency replay, secret-shaped idempotency, duplicate actions, and no-side-effect projections.

### Critical gap

Current main’s `workflow_execution_queue._is_pending_execution()` checks:

```text
record.action_key in ACTION_CATALOG
record.approval_state == "approved"
record.execution_state == "pending_execution"
```

It does **not** verify that the record has a matching approved approval-request object. Today this is not an external side-effect bug because the queue is no-op. But it becomes a serious architectural flaw the moment a future executor consumes the queue.

`codex/workflow-automation` adds the right pattern: pending execution must require a matching approved request with matching ledger/business/case/action identity and decision timestamp.

### ARB recommendation

- Prioritize `codex/workflow-automation` after rebase.
- Before any real executor lands, require:
  - matching approved approval request;
  - execution-attempt ledger;
  - external response redaction;
  - retry/replay semantics;
  - invariant that no side-effect path can bypass approval/idempotency/audit.

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### What is aligned

Recent work materially improves trust boundaries:

- Internal success/error envelopes redact business ids, request ids, messages, warnings, and data.
- Authentication denials and authorization denials are audited best-effort without persisting raw bearer tokens.
- Audit store redacts actor refs, target ids, request ids, event data, and business scope keys.
- `redact_text`, `redact_uri`, and `redact_secrets` cover common token, OAuth code, auth header, private key, URL query, and userinfo shapes.
- RBAC roles exist: `viewer`, `operator`, `admin`.

### Gaps / risks

1. **Legacy role and business scope are not production SaaS-ready.**
   - `normalize_operator_role(None)` defaults to `operator`.
   - `allowed_businesses is None` means legacy token-scoped access.
   - This is compatible for internal migration, but not acceptable for a sellable Admin surface.

2. **Audit is best-effort in auth denial paths.**
   - Fail-closed auth is correct, but privileged mutations eventually need guaranteed audit writes or an explicit policy for audit-sink outage.

3. **Global WhatsApp delivery-status route needs tenant boundary review.**
   - `/internal/brain/whatsapp/delivery-statuses` uses magic `business_id = "whatsapp"` and returns recent delivery events from `SQLiteWhatsAppDeliveryStatusStore`.
   - This may be fine for internal admin-only use, but it is not a tenant-scoped route. Before external/admin UI exposure, make it business-scoped or require admin permission with explicit cross-business audit.

### ARB recommendation

- Merge `codex/trust-admin-security` after rebase.
- Add a release blocker: external Admin requires explicit role + explicit business scope; no implicit `operator` and no token-scoped `None` grants.
- Gate global delivery-status inspection behind admin-only scope or tenant-specific route.

## Operator surface and endpoint strategy

Current main now has many operator routes for summaries, aging, stagnation, acknowledgment/handling/resolution latency, throughput, recent status changes, top lists, dashboard views, timeline, actions, audit, and runs. The service helpers are deterministic and mostly projection-only, but the route count is a strategic smell.

Atlassian-style product architecture should converge toward:

- **Case query endpoint**: JQL-lite / WorkItem field registry.
- **Facet endpoint**: group by allowlisted WorkItem fields (`status`, `status_category`, `case_type`, `severity`, `priority_bracket`, `entity.kind`, `source_connector`, time buckets).
- **Saved view registry**: built-in D2C views and later tenant-owned saved views.
- **Dashboard composition**: dashboard cards consume query/facet definitions rather than bespoke HTTP routes.

Keep the current endpoints if they are already useful, but stop adding one route per chart/card unless it is a temporary compatibility shim over the generic registry.
