# Architecture Review — 2026-06-12

Base branch reviewed: `feat/orvo-brain-control-plane`

## Executive summary

The current control-plane direction is broadly aligned with the Orvo/Jira-like target:

- `OperationalCase` remains the durable issue object, while `WorkItem` is a projection layer rather than a parallel task store (`app/brain/work_items.py:1-6`, `app/brain/work_items.py:239-327`).
- The semantic metric registry is the canonical vocabulary and is enforced in both case evidence selection and connector certification (`app/brain/semantics/metric_registry.py:132-208`, `app/brain/connector_registry.py:508-605`, `app/brain/operational_cases.py:1152-1180`).
- Connector configuration, secret resolution, adapter execution, health, and operator projections are meaningfully separated (`app/brain/config.py:28-35`, `app/brain/connector_registry.py:139-143`, `app/brain/operator_api/connectors.py`, `app/brain/connector_health.py`).
- Workflow automation already has the right safety spine: durable idempotency keys, approval requests, and a queue that only exposes approved/pending-execution actions (`app/brain/workflow_action_ledger.py:3-6`, `app/brain/workflow_action_ledger.py:181-206`, `app/brain/workflow_execution_queue.py:98-112`).
- Trust/admin/security is improving, but RBAC is still transitional/header-derived rather than a durable admin policy model (`app/brain/operator_auth.py:3-6`, `app/brain/operator_auth.py:21-23`, `app/brain/operator_auth.py:135-167`).

The biggest architectural risk is **operator-surface sprawl**: the repo now has a solid common query/view primitive (`WorkItem` metadata + JQL-lite + built-in views), but one branch expands many bespoke “recent/commented/updated/suggested” endpoints that iterate cases directly instead of leaning harder on the canonical query layer.

## Review by mission area

### 1) OperationalCase / WorkItem Atlassian-pattern alignment

### What is aligned now

The current base is directionally correct:

- `OperationalCase` is still the durable source of truth.
- `WorkItem` is explicitly a projection layer for project / issue type / workflow / status-category semantics, not a second store (`app/brain/work_items.py:1-6`).
- Business scope maps to a stable project projection/key (`app/brain/work_items.py:122-148`).
- Case type maps to issue type and release state (`app/brain/work_items.py:155-176`, `app/brain/work_items.py:258-269`).
- Workflow/status metadata is deterministic and exposed centrally (`app/brain/work_items.py:272-327`).
- Query fields are allowlisted and power JQL-lite/facets/sorts (`app/brain/work_items.py:52-113`, `app/brain/work_items.py:201-220`).
- Built-in views sit on top of the common query layer rather than inventing custom persistence (`app/brain/operator_views.py:1-4`, `app/brain/operator_views.py:68-129`).

### Gaps

1. **JQL is still intentionally partial.** This is fine for the current phase, but it means Orvo has query semantics, not yet a full Jira-class search plane.
2. **Project/workflow schemes are exposed as fixed defaults, not yet provisioned/administered artifacts.** The architecture doc expects business/workspace/project + workflow scheme + SLA policy to become first-class control-plane objects, but the implementation is still mostly static.
3. **`n2-pro-work-management` embeds SLA policy too low in the issue object path.** The branch adds useful `due_at`, `sla_target_seconds`, and `sla_status` concepts, but it currently hardcodes default SLA seconds by severity inside `app/brain/operational_cases.py`. That is workable for bootstrap, but it is not the long-term Atlassian-like shape; SLA belongs closer to a policy/scheme layer than to case mutation helpers.
4. **`N2-Pro/operator-surfaces` drifts away from the shared search/view model.** The branch adds many specialized endpoints/modules (`recent_cases.py`, `updated_cases.py`, `commented_cases.py`, `suggested_actions.py`, multiple `app/http/internal_brain/*` routes) that iterate `store.list_cases(...)` directly. That grows surface area faster than it grows platform primitives.

### Recommended direction

- Keep extending the `WorkItem`/query metadata model.
- Prefer adding fields/facets/views to the canonical query layer over adding more bespoke endpoints.
- Externalize SLA targets into a policy/scheme object before treating SLA as fully merge-complete architecture.

### 2) Semantic registry as canonical source of truth

### What is aligned now

This is one of the strongest areas in the repo.

- Canonical keys and aliases are centrally resolved by `MetricRegistry` (`app/brain/semantics/metric_registry.py:132-156`).
- Case-family evidence contracts use canonical metric keys (`app/brain/semantics/metric_registry.py:159-193`).
- Connector families are validated against declared envelopes and registry families (`app/brain/connector_registry.py:508-605`).
- Operational cases only keep evidence metrics whose keys resolve canonically and are allowed for the case family (`app/brain/operational_cases.py:1152-1180`).

### Remaining drift risk

The main residual drift is at the adapter edge:

- Several adapters still emit legacy alias keys such as `revenue_today`, `orders_today`, `stock_units`, `ad_spend_today` (`app/brain/adapters/google_sheets.py:172-228` and similar adapter modules).
- This is safe because aliases resolve through the registry, but it still expands the vocabulary that humans see in adapter code and tests.

### Recommended direction

- Keep aliases for compatibility.
- Gradually migrate first-party adapters to emit canonical keys directly, leaving alias support only for backwards compatibility and external/manual payloads.
- Treat `work_item` query metadata and operator-surface fields as separate from the semantic metric registry; do not let search/view field growth become a second metric vocabulary.

### 3) Connector platform separation: adapter / service / storage

### What is aligned now

The separation is mostly good:

- Durable connector config separates public params from `secret_refs` (`app/brain/config.py:28-35`).
- Raw credentials are meant to be resolved only at execution time, not serialized into runtime artifacts/ledgers (`app/brain/config.py:31-35`, `app/brain/connector_registry.py:139-143`).
- Registry specs declare capabilities, emitted families, required secrets, service bindings, and factory params.
- Health/readiness is projected separately from adapter execution.

### Branch note

`N2-Pro/connector-platform` is a good incremental improvement: readiness now exposes `required_scopes`, which is exactly the kind of registry-derived admin/operator metadata the platform should expose.

### Gap

No major architectural blocker here. The main thing to protect is keeping operator readiness/reporting projections thin and registry-derived, rather than letting per-connector custom logic leak into surface handlers.

### 4) Workflow automation: idempotency, approval gates, audit

### What is aligned now

This area is also strong architecturally.

- Planned actions are recorded before any future executor side effect (`app/brain/workflow_action_ledger.py:3-6`).
- Idempotency is durable and stable via hashed keys (`app/brain/workflow_action_ledger.py:181-183`).
- Approval-required actions become explicit approval-request objects.
- The execution queue only surfaces approved, pending-execution actions with matching approved requests (`app/brain/workflow_execution_queue.py:98-112`).

### Branch note

`N2-Pro/workflow-automation` stays within those constraints:

- broadens `source_connector` condition matching from one value to a normalized set;
- adds optional `case_id` scoping to workflow audit projections.

That is additive and still respects the ledger/audit model.

### Gap

The platform still projects/plans more than it executes. That is acceptable today, but once true side-effect executors land, the current ledger/approval model must remain the only path to execution.

### 5) Trust / Admin / Security: RBAC, audit, secret boundaries

### What is aligned now

- Operator auth has explicit role/permission and business-scope checks (`app/brain/operator_auth.py:21-23`, `app/brain/operator_auth.py:122-167`).
- Audit is append-only and redacted before persistence (`app/brain/operator_audit.py:1-5`, `app/brain/operator_audit.py:103-127`).
- Business scope is queryable separately from display-safe audit output.

### Branch note

`N2-Pro/trust-admin-security` is worth merging:

- secret-shaped business IDs are fully collapsed to `[REDACTED]` for display/export rather than partially preserved;
- internal auth ordering for explicit-global-scope endpoints now yields cleaner denial behavior and better audit precision.

### Strategic gap

RBAC is still a **transitional internal-operator model**:

- principal data is header-derived;
- roles are static in code;
- there is no durable admin-managed RBAC registry/policy store yet.

That is sufficient for the current internal console phase, but it is not the final trust/admin architecture for a sellable control plane.

## Highest-priority recommendations

1. **Do not merge `N2-Pro/operator-surfaces` as-is.** Refactor it toward shared case-query/view primitives first.
2. **Merge `N2-Pro/trust-admin-security`, `N2-Pro/workflow-automation`, and `N2-Pro/connector-platform`.** These improve platform correctness without creating alternate control paths.
3. **For `n2-pro-work-management`, keep the WorkItem/SLA projection work but extract SLA policy semantics upward.** The issue/workflow model is good; the policy placement needs another pass.
4. **Keep the semantic registry as the only metric vocabulary.** Over time, migrate adapters toward canonical keys to reduce alias-shaped drift.
5. **Use search/view metadata as the primitive, not endpoint count, for operator-surface growth.** If a new surface can be expressed as a built-in view, query-field addition, facet, or export over the same query layer, prefer that path.

## Bottom line

The repo is converging on the right control-plane shape. The most merge-worthy branches are the ones that **strengthen registries, audit, readiness, and deterministic workflow plumbing**. The least aligned branch is the one that **adds many bespoke operator endpoints instead of deepening the common WorkItem/query/view substrate**.
