## Executive verdict

Current `feat/orvo-brain-control-plane` remains architecturally aligned as the integration baseline. The last day of landed work strengthened the platform rather than bypassing it: case facets now flow through the WorkItem/JQL field registry, run history has dispatch-status filtering, worker manifest guards improved integration hygiene, and the deterministic `app.brain` boundary is now guarded against LLM/conversation imports.

The main ARB concern has become more precise: **the semantic registry is canonical for metric evidence, but it is not yet sufficient as the only product-release gate.** `CASE_FAMILY_METRICS` correctly prevents metric drift, but docs now distinguish “registered but readiness-gated” families such as `unanswered_conversations`. Current code treats all entries in `CASE_FAMILY_METRICS` as detectable/owner-facing and `case_type_release_state()` treats them as `promoted`. That is too coarse for a sellable D2C product where a registered metric family may still require connector/freshness/SLA/PII gates before owner-facing promotion.

Top ARB calls:

1. **OperationalCase / WorkItem: aligned baseline.** Current code follows the right Atlassian pattern: project, issue type, workflow, status category, priority bracket, WorkItem projection, and JQL-lite query primitives all derive from `OperationalCase`; no separate WorkItem store was found.
2. **Semantic registry: canonical, but release/readiness semantics need refinement.** Metric definitions and aliases are centralized, but `promoted` should not mean “present in `CASE_FAMILY_METRICS`” for every family. Add a readiness/release state that can express `metric_registered_but_readiness_gated` or equivalent.
3. **Connector platform: good direction with transitional risks.** Registry/runtime/ledger separation is credible; local `codex/connector-platform` is high-value but broad enough to require rebase and selective merge. Raw secrets must remain execution-scoped only.
4. **Workflow automation: currently safe.** The baseline execution queue is projection-only, requires a matching approved approval request, and reports `execution_enabled = False` / `side_effects_executed = 0`. Future executor work remains blocked until attempt-ledger/RBAC/retry/redaction contracts exist.
5. **Trust/Admin/Security: strong internal posture, not external SaaS-ready.** RBAC, audit, and redaction are good for internal control-plane operation; external Admin launch still requires explicit role and business claims everywhere, removing legacy implicit `operator` / token-scoped behavior.
6. **Endpoint proliferation remains the largest Atlassian-pattern product risk.** The broad operator/search branches add useful views, but Orvo should favor WorkItem/JQL/facet/view primitives over one bespoke route per dashboard card.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### Alignment

Current code follows the desired Atlassian/Jira control-plane pattern:

- `OperationalCase` remains the durable issue/workflow object. Reports, WhatsApp briefs, case queues, timelines, and action projections are not separate sources of truth.
- `app/brain/work_items.py` is a projection/registry layer, not persistence. It derives:
  - project keys from route/business scope;
  - issue types from `OperationalCaseType`;
  - release-state metadata for issue types;
  - workflow/status definitions;
  - manual vs system transition metadata;
  - status categories: `to_do`, `in_progress`, `done`;
  - priority brackets;
  - canonical WorkItem query/facet/sort fields.
- `app/brain/operator_views.py` parses JQL-lite in memory, rejects unsupported syntax, limits clause/value counts, and delegates field/operator/value validity to the WorkItem query field registry.
- System recurrence and manual workflow are now properly separated: deterministic detections can reopen terminal cases through `case_reopened`, while manual operator transitions remain bounded.
- Case facets introduced since the previous review reuse `allowed_work_item_facet_fields()` rather than inventing endpoint-local fields.

### Gaps / risks

1. **Release state is too coarse.**
   - Current `case_type_release_state()` returns `promoted` for every case family present in `CASE_FAMILY_METRICS`.
   - That works for metric drift prevention but conflicts with the catalog note that `unanswered_conversations` is “registered but readiness-gated.”
   - Recommendation: introduce a separate family readiness/promotion registry, or extend release states beyond `promoted/deferred/internal_only` so metric registration does not automatically imply owner-facing promotion.

2. **Actor taxonomy is still narrower than the contract.**
   - Code-level `ActorType` remains `system | operator`; the contract anticipates `system`, `operator`, `owner`, and `worker` timeline actors.
   - This is acceptable for current internal use, but owner replies/autonomous worker activity will need explicit actor semantics before live operator workflows become a sellable control-plane history.

3. **SLA/service semantics need to stay nested projections.**
   - `codex/work-management` and `codex/service-management` add valuable SLA/status concepts.
   - They must not mutate the canonical status category set or create a parallel service-ticket store. Treat waiting/SLA/escalation as fields/facets/projections over `OperationalCase`.

### ARB call

- **Baseline:** aligned.
- **Next work:** fix release/readiness semantics before exposing release state more broadly; merge WorkItem SLA/evidence-lineage primitives only in small slices.

## 2. Semantic registry as canonical source of truth / metric drift

### Alignment

The semantic registry is still the canonical source of business metrics:

- `app/brain/semantics/metric_registry.py` defines canonical keys, aliases, units, allowed sources, aggregation, report/case eligibility, evidence requirements, and PII class.
- `CASE_FAMILY_METRICS` gates `DETECTABLE_OPERATIONAL_CASE_TYPES` and `OWNER_FACING_OPERATIONAL_CASE_TYPES`.
- Legacy adapter/report keys such as `orders_today`, `revenue_today`, `stock_units`, `ad_spend_today`, `tiendanube.revenue_today`, and `mercadolibre.revenue_today` are mostly represented as explicit aliases.
- Evidence snapshots resolve metric keys through the registry and record alias provenance when relevant.
- Connector validation checks unknown metrics, source/family envelope mismatches, evidence requirements, value-kind errors, and money/currency requirements.

### Gaps / risks

1. **Canonical metrics are necessary but not sufficient for owner-facing release.**
   - The registry should remain the anti-drift source of truth.
   - Product readiness additionally requires connector support, freshness, SLA/business-hours policy, resolver ownership, redaction/PII safety, and stale-source suppression.
   - `unanswered_conversations` is the current example: it has canonical metrics but should not be sold as a default WhatsApp inbox module until the structured support/WhatsApp source gates pass.

2. **Some compatibility report keys still live outside the registry discipline.**
   - `reporting.py` has fallback/channel keys such as `total_revenue_today` for demo/operator compatibility. These may be harmless if not case-generating, but any owner-facing claim path should either register them as aliases or explicitly mark them rendering-only.

3. **Operator KPIs can drift even when business metrics do not.**
   - Aging, latency, dispatch, and activity summaries are workflow analytics, not commerce metrics.
   - They still need canonical field/view/facet definitions, which should remain in WorkItem/operator-view registries rather than per-endpoint calculations.

### ARB call

- **Metric registry direction:** aligned.
- **Merge gate:** no branch may add owner-facing metrics, aliases, connector emitted families, or case-family dependencies outside the semantic registry and contract tests.
- **Follow-up:** add a case-family readiness registry/state separate from `CASE_FAMILY_METRICS` membership.

## 3. Connector platform: adapter / service / storage separation

### Alignment

The connector platform is moving in the correct layered direction:

- `connector_registry.py` owns connector metadata: type, capabilities, required params, required secret refs, legacy secret fields, emitted metric/event families, executor metadata, health/rate-limit/scope/lifecycle metadata, and validation helpers.
- `runtime.py` compiles `BusinessConfig` into `CompiledBusinessRuntime` with registry-derived connector references and safe metadata; raw connector secrets are excluded from serialized runtime metadata.
- `runner.py` and `execution_ledger.py` bridge existing adapter behavior into compiled runtime/run-ledger/case paths rather than creating Tiendanube/WhatsApp shortcuts.
- `run_ledger.py` redacts secret refs and provider/error metadata and enforces terminal-run immutability.
- Current connector registry already includes post-pilot/reserved connectors such as WooCommerce, but they remain registry-defined rather than route-template shortcuts.

### Gaps / risks

1. **Legacy inline secrets are still transitional execution inputs.**
   - Current adapters still need raw values at execution time.
   - The invariant must remain: raw secrets can exist only on execution-scoped resolved copies, never in durable config artifacts, compiled runtime serialization, run ledger metadata, operator API responses, docs, examples, or audit events.

2. **Health remains metadata-first.**
   - `ConnectorHealthMetadata(readiness_check="metadata_only")` is honest.
   - Do not market self-service connector readiness until real health-history/provisioning audit storage exists with typed stale/unauthorized/rate-limit states.

3. **`fix/connector-failure-cases` is strategically important but runtime-sensitive.**
   - Turning connector failures into `data_stale` cases aligns strongly with the PRD.
   - It touches `pipeline.py`, `runner.py`, `execution_ledger.py`, and the runtime script; merge only after rebase and focused compatibility tests.

### ARB call

- **Baseline:** aligned for Phase A.
- **Merge priorities:** connector-failure-to-`data_stale` case path; connector-platform secret/executor/capability hardening.
- **No-go:** any branch that reads connector output directly into reports/cases without registry validation and ledger evidence.

## 4. Workflow automation: idempotency, approval gates, audit

### Alignment

Current workflow automation is safe-by-default:

- Manual case actions require safe `X-Idempotency-Key` at the shared helper boundary, not only at HTTP routes.
- Action keys are catalog-gated; terminal operator transitions require reasons.
- `WorkflowActionLedgerStore` reserves manual/workflow actions and supports duplicate replay/conflict behavior.
- `workflow_automation.py` is simulation/projection only; it validates rules, computes deterministic idempotency keys from redacted params, records planned actions when a ledger is supplied, and always returns `side_effects_executed: 0`.
- `workflow_execution_queue.py` now requires:
  - action key is catalog-defined and approval-required;
  - `approval_state == approved`;
  - `execution_state == pending_execution`;
  - matching approved approval-request object with matching ledger/business/case/action identity and `decided_at`.
- The queue still declares `execution_enabled = False`, `executor_state = not_implemented`, and `side_effects_executed = 0`.

### Gaps / risks

1. **Approved queue is not an executor.**
   - Future implementers may be tempted to consume the projection directly.
   - A real executor must first introduce execution-attempt ledgering, provider idempotency proof, RBAC/action-scope checks, retry/failure semantics, redacted external response audit, and tests proving no side-effect path can bypass approval/idempotency/audit.

2. **Workflow condition vocabulary should remain WorkItem/case-field aligned.**
   - `codex/workflow-automation` adds an assignee condition. That is acceptable if it uses canonical case/WorkItem fields and remains projection-only.

### ARB call

- **Baseline:** aligned.
- **`codex/workflow-automation`:** merge-ready after rebase if it remains projection-only and preserves approval matching.
- **No-go:** real side-effect execution without the executor contract above.

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### Alignment

Current internal trust posture is good for a prototype/control-plane integration surface:

- `operator_auth.py` normalizes roles (`viewer`, `operator`, `admin`) and permissions, enforces business scope when explicit grants are present, and requires explicit global scope for cross-business surfaces.
- Internal success/error envelopes redact business IDs, request IDs, data, warnings, codes/messages, and secret-shaped text.
- Failed internal authentication attempts are audited without raw `Authorization` values or token tails.
- `operator_audit.py` persists redacted, business-scoped audit events with bounded retention export.
- Global WhatsApp delivery-status inspection now requires admin permission plus explicit all-business grant.
- Run ledger, audit, operator API, and evidence models all apply defensive redaction.

### Gaps / risks

1. **Legacy auth compatibility is still not SaaS-ready.**
   - `normalize_operator_role(None)` defaults to `operator`.
   - `allowed_businesses is None` means legacy token-scoped access.
   - This is acceptable only for internal migration. External Admin launch must require explicit authenticated role plus explicit business claims.

2. **Audit is best-effort in some denial paths.**
   - Failing closed is correct.
   - Privileged mutations eventually need a deliberate policy for audit-sink outage: block mutation, queue audit, or mark degraded — but not silently continue for external production.

3. **Trust branch overlap is high.**
   - `codex/trust-admin-security` is aligned but overlaps many already-integrated redaction/admin-boundary changes. Rebase and merge only unique hardening.

### ARB call

- **Baseline:** internally strong.
- **Merge:** trust/security slices after redundancy check.
- **Release blocker:** no external Admin surface while implicit role/business scope compatibility remains enabled.

## Strategic recommendations

1. **Fix case-family readiness semantics.** Separate “metrics registered” from “owner-facing promoted.” This is the most important architectural cleanup before further operator/query exposure of release state.
2. **Prioritize degraded-state honesty.** Rebase and review `fix/connector-failure-cases`; data-source failures should create/update `data_stale` cases and narrow downstream advice.
3. **Merge primitives, not endpoint bundles.** WorkItem fields, JQL/facet registries, audit guards, and connector contracts are mergeable; bundles of bespoke recent/summary/dashboard endpoints should be split.
4. **Keep automation projection-only.** Planning, approval, idempotency, and audit are valuable now. Execution needs a separate governed executor contract.
5. **Do not let post-pilot connector breadth dilute the Tiendanube D2C wedge.** WooCommerce/Meta/MercadoLibre work must remain registry-bound and case-family-gated until it deepens the D2C control-plane story.
6. **Treat WorkItem as an issue projection, not a second issue store.** This is the core Atlassian pattern Orvo is currently preserving well.

## Final ARB call

- **Current baseline:** merge-ready and test-verified.
- **Immediate merge candidates after rebase:** test-only scope/ledger guards, `fix/connector-failure-cases`, workflow projection-only improvements, unique trust/security hardening, selected connector-platform contract hardening.
- **Needs semantic fix before merge:** release-state query/projection exposure until registered-but-readiness-gated families are not mislabeled as fully promoted.
- **Hold/split:** broad `operator-surfaces`, `search-analytics`, `work-management`, `service-management`, and `edge-developer-platform` branches unless reduced to contract-sized primitives tied to D2C pilot outcomes.
