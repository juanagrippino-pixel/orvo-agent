## Executive verdict

The control-plane baseline is materially stronger than the prior review cycle. The baseline now has the essential Atlassian-like primitives in the correct place:

- `OperationalCase` remains the canonical work item and source of truth.
- `work_items.py` adds read-only project, issue-type, workflow, and status-category projections without creating a parallel task store.
- Status categories are canonicalized as `to_do`, `in_progress`, `done`.
- JQL-lite and operator views operate over deterministic projections, not raw SQL or report text.
- The semantic registry remains the canonical source for metrics and case-family metric requirements.
- Connector execution is registry/ledger/secret-ref oriented.
- Workflow automation is ledger/idempotency/approval-gate oriented and still no-side-effect by default.
- Trust surfaces now include role permissions, business-scope checks, authorization denial audit, audit export permission, and redaction boundaries.

Main architectural risks now are narrower:

1. **Project key collisions.** Baseline derives `project_key` by truncating normalized `business_id` to 32 characters. `codex/eng-factory-project-key-hash-20260603` fixes this with a deterministic hash suffix and should be merged soon.
2. **Gateway policy as manifest vs enforcement.** `codex/edge-developer-platform` is strategically useful, but the new gateway policy registry is not yet actual gateway/proxy enforcement. Treat it as a contract/manifest layer until wired into request handling.
3. **Workflow executor gap.** Approval requests and action ledgers are correct, but approved actions must not gain external side effects until executor identity, provider idempotency, execution-attempt ledger, RBAC, and audit linkage exist.
4. **Metric drift via literals.** No reviewed branch creates a competing metric registry, but adapters and case logic still contain raw metric/family literals. New product KPIs must be registry-first.

## 1. OperationalCase / WorkItem against Atlassian patterns

### Current alignment

`OperationalCase` now maps cleanly to Atlassian/Jira primitives while preserving Orvo-specific deterministic evidence:

- **Tenant/project scope:** `business_id` is the source scope; `work_items.py` projects it into `project_id`, `project_key`, display name, case-type scheme, and workflow scheme.
- **Issue/work-item identity:** `case_id`, `dedupe_key`, and projected `work_item_id`.
- **Issue type:** `case_type` is projected as `issue_type` and exposed through issue-type definitions.
- **Workflow statuses:** `open`, `acknowledged`, `in_progress`, `resolved`, `dismissed`.
- **Status categories:** canonical mapping is `open -> to_do`, `acknowledged/in_progress -> in_progress`, `resolved/dismissed -> done`.
- **Workflow definition:** `work_items.py` publishes a deterministic workflow definition and status transition table while keeping tenant customization off.
- **Query layer:** JQL-lite is a bounded parser over projected case/work-item fields, including project, issue type, status category, assignee, severity, status, and timestamp fields.
- **Audit/history:** case timeline contains deterministic events: open/update/reopen/status change/assignment/evidence/comment.
- **Evidence:** cases hold evidence snapshots, evidence refs, metric snapshots, source connector/run metadata, and artifact refs.

This is the right architecture: reports, WhatsApp messages, dashboards, exports, and service-management views are projections. `OperationalCase` is the state owner.

### Gaps and recommendations

1. **Merge the project-key hash fix.** Truncation can collide for long business names. `codex/eng-factory-project-key-hash-20260603` adds a deterministic SHA-1 suffix while preserving max length and stability. This is the highest-priority WorkItem alignment branch.
2. **Keep WorkItem projection-only.** Do not add a WorkItem persistence table yet. If boards require persisted rank/swimlane later, add it as board metadata linked to `case_id`, not as a second lifecycle state.
3. **Avoid duplicate status-category implementations.** Baseline uses `to_do`, not `todo`. Do not merge older status-category branches that reintroduce alternate vocabulary.
4. **Treat service-management status separately.** Service-management owner statuses such as `waiting_owner` and `waiting_external` are useful, but they must remain nested projection fields, not new canonical workflow statuses.
5. **Move case-type metadata toward a registry.** `codex/work-management` adds issue-type definitions with `required_metric_keys` from `CASE_FAMILY_METRICS`. That is the right direction because it ties issue types to semantic metrics without drift.

## 2. Semantic registry canonical source of truth

### Current alignment

The semantic registry remains the canonical source of truth:

- `MetricRegistry` owns canonical metric keys, aliases, families, units, aggregation, freshness, report/case permissions, PII class, and allowed sources.
- `CASE_FAMILY_METRICS` ties detectable case families to canonical metrics.
- Connector specs validate emitted metric keys/objects through registry helpers.
- Operational cases validate evidence metrics and attach snapshots rather than using generated copy as evidence.
- Work-management branch additions refer to `CASE_FAMILY_METRICS` for issue-type required metrics instead of inventing local metric lists.

No recent branch reviewed creates a competing metric registry.

### Drift risks

1. **Adapter legacy keys remain visible.** Aliases bridge legacy adapter keys, but new adapters should emit canonical keys directly or have tests proving every emitted key resolves via `default_metric_registry()`.
2. **Derived workflow analytics are not metrics yet.** Queue totals, latency histograms, SLA projections, and throughput dimensions are valid workflow analytics. If any become product-level KPIs, register them or explicitly document them as case-state analytics, not business metrics.
3. **Connector health is not a business metric.** `codex/connector-platform` correctly treats health state as connector/run ledger taxonomy, not as semantic sales/inventory/ad metrics.

ARB recommendation: enforce “registry first for new metric semantics.” Raw metric-key literals outside registry/tests/adapters should be treated as suspicious in future reviews.

## 3. Connector platform separation: adapter / service / storage

### Current alignment

Current platform separation is broadly correct:

- `connector_registry.py` defines connector specs, secret requirements, validation helpers, capabilities, lifecycle/rate-limit/health metadata, and adapter factory metadata.
- Adapter modules remain under connector-specific adapter paths.
- Runtime and runner code compile execution plans from config/registry rather than shortcutting directly from endpoints to adapters.
- Run persistence is ledger-owned (`run_ledger.py`, `execution_ledger.py`) and redacts secret-shaped values.
- Secret refs are explicit in connector config and must not become public/operator API values.

### Branch findings

`codex/connector-platform` is now narrow and aligned. Its connector health outcome taxonomy (`ok`, `degraded`, `stale`, `unauthorized`, `rate_limited`, `failed`) belongs in platform/run metadata and improves operator diagnosis without creating metric drift.

`codex/run-api-secret-ref-boundary-20260602` is also aligned: it adds defensive API-boundary redaction for run projections, protecting against legacy/custom ledger rows that may bypass model validators.

### Recommendations

1. Merge connector health and run projection redaction after tests.
2. Keep raw `secret://...` handles strictly internal to runtime/secret-resolution boundaries; persisted ledgers and operator APIs should show `[REDACTED]` for secret-ref values while preserving safe fields such as connector id/type and secret parameter names.
3. Do not loosen adapter factory validation. Connector registry should continue to validate contracts instead of only checking “callable exists.”
4. Introduce a typed connector execution context before adding more connectors: secret resolver, HTTP client/session, clock, retry/rate-limit policy, ledger handle, and connector spec.

## 4. Workflow automation: idempotency, approval gates, audit

### Current alignment

The workflow automation baseline is correctly conservative:

- Action keys come from `ACTION_CATALOG`.
- Idempotency keys are deterministic and generated after redaction-safe payload handling.
- Duplicate planned actions are skipped by idempotency key.
- Approval-required actions are blocked with `execution_state = blocked_approval_required` and create approval requests.
- Simulation guarantees `side_effects_executed = 0`.
- Action ledger and approval records are durable and redacted.

### Branch findings

`codex/workflow-automation` adds an approval queue projection that reads the workflow action ledger and lists only pending approval requests whose ledger record is still pending/blocking execution. It explicitly declares `approval_execution_enabled = False` and `side_effects_executed = 0`. This is exactly the right service-layer surface.

`codex/work-management` strengthens audit order by rejecting backdated mutation timestamps and adds richer mutation metadata for detection-driven reopen/update. This improves case timeline trust.

### Remaining required work before execution side effects

Do not add a governed executor until these exist:

- executor actor identity and permission;
- execution-attempt ledger linked to approval request and action record;
- external provider idempotency key per action;
- dry-run parity;
- retry/failure semantics;
- redacted audit events for approve/reject/execute/fail/deny;
- explicit guarantee that WhatsApp/report text never owns case lifecycle state.

## 5. Trust / Admin / Security: RBAC, audit, secret boundaries

### Current alignment

Current baseline includes the important trust/admin slice:

- Internal shared bearer token gate remains in `app/http/internal_brain/common.py`.
- Operator roles map to permissions: `viewer`, `operator`, `admin`.
- Permissions include `internal:read`, `case:action`, and `operator_audit:read`.
- Business-scope checks use `X-Orvo-Businesses`; authorization denials can be audited.
- Operator audit events are appended through a durable store and redacted before response/persistence.
- Internal API responses set `redaction_applied = true`.
- Secret redaction covers raw tokens, secret refs, query params, and URL userinfo credentials.

### Gaps

1. **Shared token + headers are not production identity.** Good enough for internal/runtime preview, but external/live exposure needs a real operator identity provider or signed gateway principal, plus durable grants.
2. **Gateway policy is not enforcement yet.** `codex/edge-developer-platform` adds a useful in-process policy registry and route manifest, including idempotency requirements and audit event names. It should be documented as policy metadata unless wired into every internal route.
3. **Rate-limit metadata is not rate limiting.** The gateway policy branch defines buckets; it does not enforce quotas. Do not rely on it for abuse protection until enforcement exists.
4. **Audit raw-vs-redacted tradeoff remains deliberate.** Redacting before persistence is safest now. If forensic fidelity becomes necessary, add encrypted privileged raw audit payloads with break-glass controls; never store plaintext secrets.
