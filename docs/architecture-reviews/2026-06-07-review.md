## Executive verdict

The core architecture is directionally strong and increasingly resembles an Atlassian/Jira-like control plane rather than a report/chatbot system:

- `OperationalCase` is the durable source of truth for workflow state.
- `WorkItem` is correctly modeled as an additive Jira-like projection, not a second task store.
- JQL-lite/query support is allowlisted through a field registry.
- The semantic metric registry is actively used to gate case-family evidence and prevent metric drift.
- Connector registry/runtime boundaries are converging on declarative adapter execution, secret references, ledgers, and redacted metadata.
- Workflow automation is intentionally ledger-first and zero-side-effect until approval/execution infrastructure exists.
- RBAC/audit/security branches are adding the right fail-closed/redacted boundaries.

Primary ARB concern: the repo now has many overlapping feature branches that pass focused tests but diverge from the base by different amounts. Several are architecturally sound but should not be direct-merged without rebase/slicing because they mix unrelated platform/security/operator changes.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### What is aligned

Current main and `codex/work-management` show the right layered model:

- `OperationalCase` remains durable source of truth.
  - `app/brain/operational_cases.py` explicitly states cases are source of truth and WhatsApp/report surfaces are projections.
  - Statuses are lifecycle states: `open`, `acknowledged`, `in_progress`, `resolved`, `dismissed`.
  - Jira-like status categories exist: `to_do`, `in_progress`, `done`.
  - Transition table is deterministic and bounded.
- `WorkItem` is a Jira-like projection:
  - Project projection: `project_id`, `project_key`, `business_id`, scheme IDs.
  - Issue type maps to `OperationalCaseType`.
  - Workflow/status category maps to `OperationalCase` status/category.
  - JQL-lite field registry exists and is allowlisted.
  - Priority brackets, SLA timestamps, comment counts, and source connector fields are projection semantics, not separate mutable state.

This is the right Atlassian pattern for Orvo: cases are issues; WorkItems are issue projections; operator queues/boards are views.

### Gaps / risks

1. **Projection-only schemes are not yet first-class registries.**
   - Project, issue-type scheme, and workflow scheme IDs exist in projections, but there is not yet a durable/admin-owned scheme registry comparable to Jira project configuration.
   - This is acceptable for the first D2C wedge, but should be explicit: default D2C scheme only, no tenant-custom workflows until the core is stable.

2. **Endpoint proliferation risk in `codex/operator-surfaces`.**
   - The branch adds many specific recently/opened/acknowledged/assigned/commented/resolved/dismissed endpoints.
   - Strategically, Orvo should prefer a small number of generic Jira-like view/query endpoints powered by the WorkItem field registry and saved views, not one route per dashboard card.

3. **`channel_mix_shift` is present as a type but not promoted.**
   - This is intentionally deferred by tests in `codex/search-analytics` and by `OWNER_FACING_OPERATIONAL_CASE_TYPES = CASE_FAMILY_METRICS` in main.
   - Keep that boundary. Do not let title/copy heuristics open `channel_mix_shift` until `CASE_FAMILY_METRICS` has canonical metrics and tests.

### ARB recommendation

- Merge `codex/work-management` after rebase.
- Require `codex/operator-surfaces` to consolidate endpoint additions into a reusable view registry/JQL contract before merge, or split out only low-risk endpoints already backed by generic query semantics.

## 2. Semantic registry as canonical source of truth

### What is aligned

The metric registry is doing the right job:

- `MetricRegistry` owns canonical keys, aliases, definitions, allowed sources, aggregation semantics, report/case allowed flags, evidence requirements, and PII class.
- `CASE_FAMILY_METRICS` is the case-family evidence contract.
- `OperationalCase` gates detectable and owner-facing case families through `CASE_FAMILY_METRICS`.
- Evidence snapshots resolve aliases to canonical metric keys and skip unregistered metrics.
- Strict validation raises `UnknownMetricError`; advisory mode records `metric_registry_issues` without inventing metrics.
- Tests cover registry contracts, case-family promotion policy, adapter metric emission, and validation.

### Gaps / risks

1. **Advisory validation can hide future drift if not monitored.**
   - `_metric_registry_metadata(report)` records advisory issues in case metadata, but that metadata can become passive unless dashboards/CI surface it.
   - Recommendation: add a periodic invariant/report that counts advisory unknown-source/unknown-key issues per connector and fails CI for new production connector drift.

2. **Deferred case types must not accumulate.**
   - `channel_mix_shift` is explicitly deferred. That is fine.
   - Any new case family must be promoted only by adding registry metrics, case-family tests, evidence snapshot tests, and operator projection tests in the same branch.

### ARB recommendation

- Treat `CASE_FAMILY_METRICS` as the release gate for every owner-facing or detectable OperationalCase family.
- Reject branches that add case types, operator cards, or WhatsApp copy for unregistered case families unless they are explicitly marked as deferred and excluded from owner-facing projections.

## 3. Connector platform separation: adapter / service / storage

### What is aligned

Main and `codex/connector-platform` are moving in the right direction:

- Connector metadata lives in `connector_registry.py`, not in route handlers.
- Runtime planning validates registered connectors and required config/secret references.
- Adapter factories are declared through registry metadata instead of hardcoded branching.
- Secret refs are modeled separately from public params.
- Execution/run ledgers and redaction helpers prevent raw connector details from becoming operator-facing state.
- Branch tests cover compiled runtime secret refs, connector registry, runtime, runner, secret redaction, and route auth.

### Gaps / risks

1. **`codex/connector-platform` is too broad/stale for direct merge.**
   - Divergence is `78 behind / 72 ahead`; diff touches 65 files and includes substantial operator/security/test changes beyond pure connector-platform concerns.
   - This increases merge risk and makes architecture review hard to reason about.

2. **Legacy inline secret params still exist during transition.**
   - The design correctly permits execution-scoped legacy adapter params, but durable config must remain `secret_refs` only.
   - Any merge must ensure raw access tokens never enter compiled runtime metadata, run ledger, operator API responses, or audit events.

3. **Health/readiness remains mostly metadata-first.**
   - That is acceptable now, but self-service connectors need real health checks and failure taxonomy before broad marketplace/developer positioning.

### ARB recommendation

- Do not direct-merge `codex/connector-platform` as-is.
- Rebase it, then split into smaller branches:
  1. connector registry metadata only,
  2. secret-ref runtime boundary,
  3. execution/run ledger metadata,
  4. connector health/readiness.
- Keep adapter implementations behind registry/runtime contracts; no Tiendanube/WhatsApp shortcuts.

## 4. Workflow automation: idempotency, approval gates, audit

### What is aligned

`workflow_action_ledger.py` and `codex/workflow-automation` are architecturally strong:

- Every planned action is ledgered before execution.
- Idempotency keys are durable and business-scoped.
- Approval-required actions create approval request objects.
- Approval decisions return records with `side_effects_executed: 0`.
- Execution queue is a projection only:
  - requires matching approved approval request,
  - requires `approval_state=approved`,
  - requires `execution_state=pending_execution`,
  - returns `execution_enabled: False`, `executor_state: not_implemented`, `side_effects_executed: 0`.
- Operator manual action idempotency tests cover duplicate, pending, failed-validation, missing-key, and secret-shaped key cases.

This avoids the key anti-pattern: an LLM/operator projection directly mutating cases or calling external systems.

### Gaps / risks

1. **Future executor contract is intentionally absent.**
   - Good for now, but before enabling side effects, Orvo needs a separate audited execution-attempt ledger with retry, terminal failure, external response redaction, and replay semantics.

2. **Approval queue and execution queue should stay distinct.**
   - Do not let UI approval imply execution. Approval should only move action state to `pending_execution`; a separate executor must consume it with its own audit and idempotency boundary.

### ARB recommendation

- Merge `codex/workflow-automation` after rebase.
- Add a blocking invariant before any real executor: no code path may execute external side effects unless it writes an execution-attempt ledger event and verifies approval/idempotency state.

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### What is aligned

Main plus `codex/trust-admin-security` show the right security model:

- Roles: `viewer`, `operator`, `admin`.
- Permissions: `internal:read`, `case:action`, `operator_audit:read`.
- Business allowlist parsing supports explicit grants and fail-closed empty grants.
- Actor refs, role labels, business values, request IDs, idempotency keys, payloads, and audit exports are redacted/sanitized.
- Operator audit store/export paths exist and have tests.
- Failed authentication/authorization attempts are audited best-effort without leaking bearer tokens or caller-controlled secret-shaped values.

### Gaps / risks

1. **Legacy token-scoped behavior remains permissive.**
   - `allowed_businesses is None` means legacy token-scoped migration mode rather than explicit business grant.
   - This is acceptable for internal migration, but not for a sellable admin console.
   - Before externalizing Admin/Trust surfaces, require explicit business scope headers/claims.

2. **Default role is `operator`.**
   - This preserves compatibility but grants mutation permissions to legacy token callers.
   - For production SaaS, default should become least privilege (`viewer`) or require explicit role claims.

3. **Audit is still best-effort in some boundaries.**
   - Good for availability, but privileged mutations should eventually support guaranteed audit writes or fail closed where legally/operationally required.

### ARB recommendation

- Merge `codex/trust-admin-security` after rebase.
- Add roadmap item: “turn off legacy operator default / require explicit role + business claims before external Admin launch.”

## Strategic alignment with sellable D2C control plane

Aligned:
- The platform core is deterministic and evidence-backed.
- Operator surfaces are case/work-item projections, not chat state.
- Workflow automation is safe-by-default and audit-first.
- Metrics are registry-owned.
- Connectors are registry/runtime-owned.
- Security work is moving toward RBAC + audit + redaction.

Watch-outs:
- Avoid generic platform positioning from `edge-developer-platform` before D2C ecommerce workflows are deep enough.
- Avoid route/card proliferation in `operator-surfaces`; prefer Jira-like view/query primitives.
- Avoid broad integration branches that mix connector, operator, security, and tests. They pass focused tests but are hard to review/merge safely.

   - New case family → must update `CASE_FAMILY_METRICS` or explicitly mark deferred and exclude from owner-facing/detectable sets.
   - New action key → must declare approval/side-effect/idempotency semantics in action catalog and ledger tests.
   - New connector → must use registry + compiled runtime + run ledger + secret refs; no route/runtime shortcut.
   - New operator surface → must be projection-only, business-scoped, RBAC-protected, audit-safe, and preferably backed by WorkItem query/view registry.
   - New admin/trust surface → must require explicit permission and business scope; no raw secret/token/idempotency echo.
