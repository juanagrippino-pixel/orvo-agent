## Executive decision

Current `feat/orvo-brain-control-plane` is architecturally aligned enough to keep as the integration baseline. It has materially improved toward an Atlassian/Jira-like control plane: Operational Cases are the durable source of truth, WorkItems are projections, JQL-lite is allowlisted, operator case actions are ledgered/idempotent at the HTTP boundary, audit/redaction tests are strong, and connector/runtime metadata is registry-driven.

The main risk is **branch proliferation and duplicated operator surfaces**. Several branches are strategically useful but broad/diverged. Merge should proceed by selective, rebased slices rather than by bulk-merging all endpoint expansions.

## 1. OperationalCase / WorkItem vs Atlassian patterns

### Alignment

- `OperationalCase` remains the durable issue record. `app/brain/work_items.py` correctly presents a Jira-like projection layer rather than creating a parallel task store.
- WorkItem projection includes core Atlassian concepts:
  - project: `project_projection`, `project_key_for_business`, `case_project_key`
  - issue type: `case_issue_type`, `operational_case_issue_type_definitions`
  - workflow/statuses: `operational_case_workflow_definition`, `operational_case_status_definitions`
  - status categories: `to_do`, `in_progress`, `done`
  - priority scheme: `priority_bracket_for_score`, `operational_case_priority_definitions`
  - JQL-lite field registry: `work_item_query_field_definitions`, `work_item_query_field_spec`
- `operator_views.py` correctly treats JQL-lite as an in-memory allowlisted projection layer, not SQL translation. It rejects unsupported fields/operators, limits clause/value counts, and bans dangerous syntax.
- System recurrence can reopen terminal cases through deterministic detections (`case_reopened`) while manual operator workflow transitions remain constrained. That matches the desired split between deterministic runtime updates and governed operator transitions.

### Gaps / risks

- The current workflow model is still a single default scheme (`tenant_customizable: False`). This is acceptable for the D2C wedge but should be documented as a deliberate phase-A constraint, not as a generic Jira replacement.
- `codex/work-management` contains important Jira-like additions not yet integrated into HEAD: SLA projection, activity timestamp invariants, transition boundaries, evidence lineage, reassignment/reopen SLA handling, and due fields. These are high-value, but the branch is broad and diverged.
- JQL-lite is intentionally small. That is good for safety, but merge candidates adding more fields should be forced through the canonical WorkItem query field registry. Avoid ad hoc filters per endpoint.

### ARB decision

- **Current HEAD:** merge-ready as baseline.
- **`codex/work-management`: needs rebase, then high-priority staged merge.** Prefer merging SLA/activity/lineage invariants in small slices, not as one large branch.

## 2. Semantic registry as canonical source of truth / metric drift

### Alignment

- `app/brain/semantics/metric_registry.py` is the canonical metric registry. It defines canonical keys, aliases, allowed sources, units, aggregation, case/report eligibility, evidence requirements, PII class, and case-family metric envelopes.
- Operational case detection derives detectable/owner-facing case types from `CASE_FAMILY_METRICS`, reducing drift between case families and metric contracts.
- Case evidence snapshots resolve aliases to canonical keys via `registry.try_resolve_key` and retain `source_metric_key` metadata only when an alias was used.
- Connector validation paths call registry-backed validators (`validate_emitted_metric_objects_for_connector`, source/family/value/currency/evidence validators).
- Current tests include metric validation and secret-redaction invariants; both passed.

### Gaps / risks

- Report-to-case validation currently records registry violations as advisory metadata (`metric_registry_mode: advisory`) rather than always blocking downstream case creation. This may be acceptable for migration but should not become the long-term control-plane contract.
- Hardcoded metric strings still appear in a small set of platform files outside the registry, primarily in `operational_cases.py` and `connector_registry.py`. Most are contract references or registry use, but future changes should avoid adding literal metric keys outside registry/tests/docs.
- `channel_mix_shift` is listed as an `OperationalCaseType` literal, but `DETECTABLE_OPERATIONAL_CASE_TYPES` and `OWNER_FACING_OPERATIONAL_CASE_TYPES` are derived from `CASE_FAMILY_METRICS`, which currently does not include `channel_mix_shift`. This is likely intentional future capacity, but it should be called out explicitly to avoid assuming the case type is active.

### ARB decision

- **Metric registry direction:** aligned.
- **Merge gate:** any branch adding metrics, case families, or connector emitted families must update the semantic registry and contract tests first; no copy-layer or endpoint-local metric aliases.
- **Needs follow-up:** decide when registry violations graduate from advisory warnings to blocking for case-generating paths.

## 3. Connector platform: adapter / service / storage separation

### Alignment

- `connector_registry.py` is now a proper connector registry with connector type, capabilities, emitted metric families, secret requirements, executor metadata, health/rate-limit/scope/lifecycle metadata, and validation helpers.
- `runtime.py` compiles `BusinessConfig` into an audit-safe `CompiledBusinessRuntime`. It keeps raw connector secrets out of serialized runtime metadata and emits connector references, secret parameter names, executor factory paths, capabilities, health policies, scopes, rate limits, and lifecycle metadata.
- `runner.py` uses compiled runtime metadata and the run ledger before invoking the existing daily report pipeline.
- `execution_ledger.py` bridges legacy pipeline outputs into run-ledger artifacts, connector outcomes, metric certification metadata, data-stale cases, and owner case briefs.
- `run_ledger.py` is append-oriented and redacts secret-shaped config refs, URI values, provider refs, error summaries, and metadata.

### Gaps / risks

- Current runtime still bridges to legacy adapter execution boundaries. That is expected during migration, but the compiled runtime should eventually become the sole path for scheduled/operator-triggered connector execution.
- `codex/connector-platform` has strong improvements (centralized daily runtime filtering, secret requirement metadata, executor metadata, event family certification), but it overlaps current `runtime.py`, `runner.py`, `connector_registry.py`, and `execution_ledger.py`; it is diverged and should be rebased carefully.
- Connector health checks are mostly metadata policies today. Real readiness checks can be added later, but should not be faked as live verification.

### ARB decision

- **Current connector platform:** aligned for phase-A.
- **`codex/connector-platform`: merge-ready in concept, needs rebase and selective conflict resolution.** Prioritize registry-driven filtering and secret binding tests.

## 4. Workflow automation: idempotency, approval gates, audit

### Alignment

- Manual case actions at the internal HTTP boundary require `X-Idempotency-Key` and write to `WorkflowActionLedgerStore` before side effects. Duplicate executed requests replay as `skipped_duplicate`; pending/failed conflicts fail closed.
- Action keys are catalog-gated. Operator API only enables safe internal case actions; external/provider actions remain disabled at this boundary.
- Terminal operator transitions require non-empty reasons. That is important for auditability.
- `workflow_automation.py` is deliberately simulation/dry-run only. It creates deterministic idempotency keys, projects approval gates, redacts params, records planned workflow actions when a ledger is supplied, and always reports `side_effects_executed: 0`.

### Gaps / risks

- `apply_case_action_with_idempotency` still accepts a missing idempotency key at the service-function level and falls back to direct mutation; the HTTP route enforces the key before calling it. For stronger architecture, the service helper should also fail closed unless a specifically named non-ledgered test/helper path is used.
- `codex/eng-factory-required-case-action-idempotency-20260606` addresses the helper-level invariant and should be reconciled.
- `codex/workflow-automation` adds useful conditions and approval identity/gate behavior, but it should remain projection/ledger-only until a governed executor contract exists. Do not allow automation to mutate cases or dispatch external actions directly.

### ARB decision

- **Manual HTTP action path:** merge-ready.
- **Service helper idempotency:** needs hardening via a rebased idempotency branch.
- **`codex/workflow-automation`: needs rebase; merge only dry-run/planning/audit slices unless executor governance is explicitly specified.**

## 5. Trust / Admin / Security: RBAC, audit trail, secret boundaries

### Alignment

- `operator_auth.py` supports scoped operator sessions with role/permission checks.
- Internal HTTP helpers emit safe envelopes and redact secret-shaped business IDs, actor refs, error codes/messages, headers, payload metadata, Basic auth attempts, and audit data.
- `operator_audit.py` appends redacted, queryable audit events with actor, business, request, target, event type, and payload metadata. Secret-shaped actor refs collapse to `[REDACTED]`.
- Current tests cover redaction of Basic auth, invalid idempotency keys, actor spoofing, failure/denial audit events, admin-only audit export, and internal error envelope behavior.

### Gaps / risks

- Header-derived identity is currently appropriate for internal/admin surfaces, but production-grade auth still needs an explicit trust boundary in front of these internal routes (gateway/service auth), not just route-local header parsing.
- `codex/trust-admin-security` is small and aligned, but overlaps current safe error/actor changes. It should be rebased and reviewed for duplicate or superseded assertions.
- `codex/edge-developer-platform` includes broader gateway policy/service catalog work. It is strategically relevant but bigger than the current D2C wedge and should not block the sellable ecommerce control-plane path.

### ARB decision

- **Current trust/security posture:** strong for internal prototype/control-plane integration.
- **`codex/trust-admin-security`: likely merge-ready after rebase.**
- **`codex/edge-developer-platform`: needs-work/park unless gateway policy is required for the next release milestone.**

## Strategic recommendations

1. **Keep OperationalCase as source of truth; WorkItem remains projection.** Do not introduce a separate task/work item persistence model yet.
2. **Promote registry failures deliberately.** Keep advisory mode only as a migration bridge. Define the milestone where connector/case metric violations become blocking.
3. **Merge platform branches in contract-sized slices.** Prioritize: WorkItem SLA/activity invariants, connector secret/runtime filtering, service-level idempotency requirement, and trust hardening.
4. **Stop endpoint proliferation.** Operator surfaces should use shared projection services and view registries; avoid one-off `/recently-*` endpoint variants unless they are defined in the operator surface contract.
5. **Protect workflow automation boundaries.** Until a governed executor exists, workflow automation may plan, audit, dedupe, and request approval — but must not mutate cases or call external systems directly.
6. **Keep D2C wedge focus.** Service catalog/gateway/service-management work is valuable platform depth, but should not outrank Tiendanube/WhatsApp-first D2C operator workflows unless explicitly tied to the wedge.
